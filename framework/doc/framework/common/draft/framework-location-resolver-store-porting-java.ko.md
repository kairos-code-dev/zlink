# Location Resolver/Store 포팅 진행 — Java (+ Kotlin)

> 이 문서는 [framework-location-resolver-store.ko.md](framework-location-resolver-store.ko.md)
> 계약을 Java framework(그리고 java 런타임을 공유하는 Kotlin 레이어)에 적용하는 작업의 진행
> 추적 문서다. 계약 내용은 반복하지 않는다. 계약이 궁금하면 항상 원본 draft를 보고, 두 문서가
> 충돌하면 원본 draft가 기준이다.
>
> spot 메시징 표면(캐시 제거, `ZLinkSpotAddress` 반환)은
> [framework-spot-address-messaging.ko.md](framework-spot-address-messaging.ko.md)가 우선한다.
> 두 draft를 함께 읽고 포팅한다. 단, spot 메시징 표면 자체의 전환(rid-only overload 제거,
> stale 주소 fail-fast 분류, bridge relay framing)은 spot-address draft의 별도 작업이며
> (dotnet 포함 미구현) 이 문서의 범위가 아니다. 이 문서 범위에서는 resolver가 spot full
> 주소(`ZLinkSpotAddress`)를 반환하는 조회 표면까지 맞춘다.
>
> 다른 언어 진행 문서: [node](framework-location-resolver-store-porting-node.ko.md) ·
> [cpp](framework-location-resolver-store-porting-cpp.ko.md).
> 전체 순서는 **node → java(+kotlin) → cpp**이며 java는 node 다음이다.


> **후속(2026-07-04)**: 이 문서의 이식 완료분 위에 POSD 재설계 2차 wave가 예정되어 있다.

## 2. 현재 상태 (2026-07-03 조사)

- location 계약 코드 0건 (`LocationStore`/`PeerLocation`/`OwnerLease` 등 키워드로 java/kotlin
  main 소스 grep 0건). 위치조회/자동연결은 전부 core native `Discovery`/`Registry` 위임:
  - 자동 연결: `runtime/channels/ZLinkChannelRuntime.java`(`discoveryFor` → 각 socket
    `attachDiscovery`), `runtime/spots/SpotDiscoveryReconciler.java`(spot mesh 100ms reconcile
    loop — 원본 §14의 정확한 대응물, store 기반으로 교체 대상)
  - spot resolve: `runtime/registry/ZLinkRegistrySpotRemoteAddressResolver.java` →
    `discovery.resolveSpot()` (진입점: `runtime/actors/ZLinkActorRuntime.java`,
    `runtime/spots/ZLinkSpotRuntime.java`)
  - embedded registry: `registry/ZLinkEmbeddedRegistryOptions.java`,
    `runtime/registry/ZLinkRegistryRuntime.java`
  - topology query: `registry/` 패키지 (`ZLinkRegistryQuery`, `ZLinkMemberPeerEntry`,
    `ZLinkRegistryTopologyEntry` 등)
  - native 종단: `runtime/binding/ZLinkJavaBackendAdapterFactory.java`의 `JavaDiscovery` record.
    backend 경계: `runtime/backend/ZLinkBackendDiscovery.java`
- 현행 lifecycle 위치 등록: framework가 row를 직접 쓰지 않고 native가 관리
  (`discovery.setSpotOwnerSyncEnabled(true)`, `SpotDiscoveryReconciler.bindLocalRouterEndpoint()`의
  `bindRoute`, `spotNode.createActor()`의 native actor route). 이 지점들이 location runtime
  write 훅으로 교체된다.
- kotlin(`zlink-framework-kotlin`)은 core·stream connector·coroutines에 의존하는 얇은 확장
  레이어(파일 7개, 전부 확장 함수/coroutine 어댑터, 별도 런타임 없음). location 관련 kotlin
  표면 0건.
- 등록 패턴: `configuration/ZLinkFrameworkOptions.java` →
  `runtime/configuration/ZLinkFrameworkRegistration.java`에 축적,
  `runtime/host/ZLinkFrameworkRuntime.java`가 `runtimeHandlers.create(type)`로 인스턴스화.
  타입 등록 선례는 `addSpotRemoteAddressResolver(Class<...>)`. Spring 경로는
  `zlink-framework-spring-boot-starter`.

### 3.1 언어가 달라도 지켜야 하는 것 (원본 draft 역참조)

- **key 직렬화 바이트 호환** — `ZLinkLocationKeyCodec`의 canonical 문자열(길이 prefix 세그먼트,
  rid는 소문자 hex, auto-connect type/role은 canonical 소문자 문자열)은 언어와 무관하게 같아야
  한다(§6.5). 서로 다른 언어 node가 같은 Redis를 공유하는 것이 전제다.
- **owner lease와 location row는 같은 물리 저장소**(§6.6) — `NewClaim`의 만료 판정 원자성.
- **resolver에 캐시 없음** — 모든 조회가 store에 도달(§8, §10).
- **claim-then-activate** 순서(§17)와 `IgnoredStale` 소유권 상실 규칙(§9).
- **compatibility wrapper 없음** — 기존 registry/discovery API는 한 번에 제거한다(§20.1).
- **레거시 코드는 작업하면서 정리한다** — 각 단계에서 새 location 표면으로 교체한 지점의
  레거시 코드(registry/discovery 계약·런타임·설정, dead config, 미사용 import/헬퍼/테스트)는
  다음 단계로 미루지 않고 그 단계에서 함께 삭제한다. deprecated 표기, 주석 처리, 죽은 코드로
  남기지 않는다. P8은 잔여분 최종 확인과 회귀 가드 추가 단계이지, 정리를 모아두는 단계가
  아니다.
- **wall clock 금지** — lease 만료는 store 기준 시각 + local monotonic 경과로만 판정(§6.6, 7.5).
- 바로 구현할 수 없는 항목은 feature map에 gap으로 남기고, sample에 private helper나 raw 우회
  경로를 넣지 않는다(§21 포팅 순서 4).
- **공통 e2e/sample 문서는 이미 location store 기준으로 변경되어 있다** — 공통 e2e 시나리오
  문서(`framework/doc/framework/common/e2e/` config-1~8)와 공통 sample 문서
  (`framework/doc/framework/common/sample/`)가 검증 기준 정본이다. e2e/sample 구현을 이
  문서들에 맞춰 변경해야 하며, 코드에 맞춰 문서를 되돌리지 않는다.
- **버그는 회피하지 않는다** — 진행 중 버그를 발견하면 우회(workaround, 재시도 감싸기, 테스트
  완화, 시나리오 축소)하지 않는다. 원인을 파악하고, 그 버그를 재현하는 회귀 테스트를 먼저
  작성한 뒤, 버그를 수정하고 나서 하던 작업을 이어간다. 버그가 기존 framework/core에 있어도
  같은 원칙을 적용한다.
- 포팅 완료 판정은 원본 draft **§24 구현 적용 확인표**를 java(와 kotlin 표면)에 적용해서 한다.
  단, §24.3의 cache 관련 항목("대체 예정" 표기 2건)은 spot-address draft의 캐시 제거 결정에 따라
  "구현하지 않음"이 정답이다 — cache를 만들면 안 된다.

## 7. 완료 처리 기준 — codex 리뷰 게이트

이 문서의 모든 작업 항목(java P1~P11과 kotlin K1~K5)이 구현·검증 통과로 체크된 뒤에도, 아래 두
가지 codex 에이전트 리뷰 게이트를 통과해야 문서를 완료 처리한다. codex 리뷰는 한 요청에 한
항목만 담고, 두 리뷰의 병렬 실행은 허용한다.

1. **적용 완결성 리뷰** — 원본 draft 계약(§24 확인표 포함, cache 항목은 3.1의 단서 적용)과 이
   문서의 체크리스트를 기준으로, java 구현과 kotlin 어댑터 표면에 누락되거나 왜곡 적용된 계약이
   없는지 리뷰한다.
