[3] F-I1-03(rererere) — bind/idempotent dual re-validate
  Diff: mesh_stream_session_api.cpp — `if (!idempotent) { re-validate }` became
  unconditional `{ re-validate }` (both insert and idempotent paths re-validate
  node->actors for absence/generation-mismatch/draining before reporting success).
  Read full function (mesh_stream_session_api.cpp:572-712) and
  session_bindings_remove_actor (:1200-1222) and destroy path
  (mesh_actor_api.cpp:600-745).
  Formal correctness argument constructed independently (happens-before chain):
    - actor.generation is a node-wide strictly-increasing counter
      (mesh_actor_api.cpp:436,476: `actor.generation = node->next_actor_generation`,
      `next_actor_generation += 1`) — a destroyed generation value can never recur.
    - destroy sets draining=true under node->mutex (mesh_actor_api.cpp ~638) BEFORE
      its wait loop, node->actors.erase (~718), and its final unconditional
      session_bindings_remove_actor sweep (~739, matches by exact actor_id+generation,
      removes ALL live bindings for that generation regardless of insertion time).
    - If a bind call's re-validate (node-mutex CS) observes "not stale", then by the
      mutex total-order property, destroy's draining-set CS (if any occurs at all for
      that generation) must be ordered strictly after that re-validate CS — otherwise
      the read would have observed draining=true. This gives a real happens-before
      edge: bind-insert -> bind-revalidate(not stale) -> destroy-draining-set ->
      destroy-erasure -> destroy-final-sweep (program order in destroy thread).
    - Happens-before is transitive across different mutexes (registry_lock vs
      node->mutex): once established, the destroy's final sweep (registry_lock CS) is
      guaranteed to observe and remove any binding inserted earlier in this chain,
      even though that insert used a different mutex (registry_lock) than the
      ordering-establishing steps (node->mutex).
    - Conclusion: any call that reports "not stale" (success) is provably followed,
      if a destroy for that generation ever executes, by that destroy's guaranteed
      removal of the binding — no orphaned binding without a corresponding cleanup
      opportunity. The original iteration-4 defect (idempotent skipped re-validate
      entirely, so it could report success for an ALREADY-fully-destroyed generation
      whose sweep had already run and would never run again) is closed because the
      idempotent path now performs the identical re-validate the inserting path does.
    - Verified session_bindings_remove_actor's removal criterion is exact
      (actor_id, generation) match, so a concurrent stale-cleanup from one racer
      cannot remove a live binding of a *different*, newer generation for the same
      actor id (a new registration would carry a newer generation value the stale
      check compares against).
  Verdict: F-I1-03(rererere) RESOLVED — confirmed by argument, independent of the
  new test's own coverage (see [7] CS-I3-02 for a separate note on the test itself).
