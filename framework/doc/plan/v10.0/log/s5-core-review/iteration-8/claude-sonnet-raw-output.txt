3. The "narrow scope" red flag
   - While reading pin_node_lifecycle's implementation I noticed it operates
     on a raw void* handle exactly like the *original*, still-existing
     as_mesh_node() function — and CS7-I1-02's own "수정 범위" section
     explicitly diagnosed the root cause as "as_mesh_node가 반환하는 raw
     pointer에 registry lock 검사와 실제 사용 사이의 수명 보장이 없다는
     근본 문제" and offered two possible fixes, one of which was "node에
     registry-lock 보호 참조 카운트를 추가해 as_mesh_node가 반환하기 전에
     pin하는 방식". The coordinator implemented pin/claim as two *new*,
     narrowly-named functions (pin_node_lifecycle, claim_node_destroy) used
     *only* by shutdown and destroy, rather than generalizing as_mesh_node()
     itself.
   - Grepped every as_mesh_node() call site across core/src/api/mesh/*.cpp:
     `grep -c "as_mesh_node (" core/src/api/mesh/*.cpp` -> mesh_api.cpp 15,
     mesh_node_api.cpp 16, mesh_actor_api.cpp 9, mesh_stream_session_api.cpp
     6, mesh_dispatch_api.cpp 5, mesh_transfer_api.cpp 4,
     mesh_messaging_api.cpp 2, mesh_monitor_api.cpp 1 = 58 total. Every one of
     these still uses the unguarded as_mesh_node() (mesh_runtime.cpp:503-514)
     which releases the registry lock at :510 before returning the pointer at
     :513, with zero pin.
   - Sampled several representative call sites and manually measured the gap
     between as_mesh_node() and the first node->mutex acquisition:
     zlink_mesh_node_connect_peer (mesh_node_api.cpp:531-558, ~22 lines of
     validation/string construction in between), zlink_mesh_node_status
     (:799-809), node_channel_submit (mesh_messaging_api.cpp:340-379, the
     shared body of 4 public send/request entry points, real validation work
     between the check and the lock), zlink_mesh_node_set_ready_handler
     (mesh_dispatch_api.cpp:172-180). Also found on_operation_timeout
     (mesh_messaging_api.cpp:27-46) — an internal callback run on the
     *detached timer thread* — uses the same unguarded pattern, meaning this
     isn't limited to application-thread callers.
   - Cross-checked spec 01-mesh-node.ko.md §11: "send, request, publish,
     weight 변경, peer intent와 query는 thread-safe다" plus destroy's own
     contract ("destroy는 먼저 child handle이 없는지 검사한다", §3, listing
     only publisher/facade-timer/monitor/session as children) — destroy does
     NOT wait for in-flight calls to these "thread-safe" operations, which
     means the implementation is *supposed* to make them safe against a
     concurrent destroy without the caller having to serialize externally.
     Checked whether this could instead be an implicit "caller must not
     destroy while other calls are in flight" contract (common in other
     C APIs) by searching for such wording anywhere in core/doc/spec/core;
     found none for MeshNode, and found the opposite precedent in
     01-context.ko.md (zmq_ctx_term-style: blocking ops return ETERM cleanly
     rather than being caller-serialized) which supports the "should be made
     safe by the library" reading. Concluded this is a genuine, broad
     residual instance of the exact same defect class as CS7-I1-02, just left
     unfixed at 58 other call sites (filed as CS8-I1-01, high).

4. Attempted dynamic corroboration for CS8-I1-01
   - No deterministic pause hook exists for any of these 58 call sites
     (unlike shutdown, which now has zlink_test_set_shutdown_pause_after_pin).
   - Wrote a standalone ASAN repro outside core/ (scratchpad/uaf_repro.cpp,
     uaf_repro2.cpp) linking against core/build-asan's libzlink, using only
     public API (zlink_mesh_node_status racing zlink_mesh_node_destroy).
   - Run 1: 20,000 single-shot races (thread spawned, one status() call,
     main immediately destroys) — no crash. Likely too much thread-creation
     latency for the racer to reach as_mesh_node before destroy completes.
   - Run 2: 800 outer iterations x 6 racer threads x 3,000-call bursts of
     status() racing one destroy() each (~14.4M calls total) — no crash
     either, in ~4 minutes of ASAN execution.
   - Concluded this is expected: even the *proven* shutdown/destroy race
     required a dedicated pause hook to become reproducible (iteration 7's
     own test_destroy_during_shutdown_wait_is_deadlock_error covered only
     the "parked in drain wait" interleaving; the pin~lock window needed the
     brand new pause hook in iteration 8 to be provable at all). Documented
     the attempt honestly in the review as inconclusive-by-design rather than
     treating non-reproduction as evidence of safety, and recommended the
     coordinator add an analogous pause hook to a representative entry point
     as the correct verification path.

6. Reading handle_reply's OOM tail more closely (led to CS8-I1-03)
   - While verifying that mesh_wire_ingress.cpp's per-message barrier really
     covers the two locations CS7-I1-01 originally called out
     (actor_apply_remote_join_reply's kind_data vector at
     mesh_actor_api.cpp:375-377, and handle_reply's ACTOR_LOOKUP kind_data
     vector at mesh_wire_ingress.cpp:618-620), read handle_reply in full
     (mesh_wire_ingress.cpp:554-627).
   - Noticed op is unconditionally erased from node_->operations at :571-576
     ("이미 완료됨: exactly-once") *before* either the ACTOR_JOIN or
     ACTOR_LOOKUP kind-specific tail runs. If that tail throws bad_alloc, the
     outer per-message catch in run_ingress_loop prevents process
     termination but just does `continue` — meaning complete_operation is
     never called for this op, and since op is already gone from
     node_->operations, no later timeout sweep or shutdown force-completion
     (which iterates node->operations, mesh_node_api.cpp:425-431) can ever
     find it either. The requester is left waiting forever with no signal.
   - For the ACTOR_JOIN accepted branch specifically, read
     actor_apply_remote_join_reply (mesh_actor_api.cpp:303-382) end to end:
     it commits the actor's spot_rid/spot_generation/spot_node_rid/
     membership_epoch under node_->mutex at :349-353 *before* constructing
     the kind_data vector at :375-377 that can throw. This means a bad_alloc
     there leaves the membership change already committed while the
     requester who initiated the join never finds out — worse than "losing
     the message in transit" (the coordinator's own justification for the
     message-level barrier design, iteration-7 finding-ledger.ko.md §2.2)
     because a genuinely lost wire message would never have caused this
     local commit or removed the local operations-map entry that would
     otherwise let it time out.
   - Filed as CS8-I1-03 (medium — real correctness/liveness violation of the
     "every operation eventually completes" invariant this very iteration
     was supposed to establish, but narrow OOM-only trigger, no crash or
     memory corruption, so not high).
