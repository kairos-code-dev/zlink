2. N6-I1-02 verification (shutdown/destroy)
   - Read mesh_node_api.cpp:310-479 (zlink_mesh_node_shutdown,
     zlink_mesh_node_destroy) in full.
   - Traced all 4 interleavings by hand:
     a. shutdown parked in cv.wait_for -> destroy checks shutdown_active
        under lock, fails fast with EDEADLK/CLOSE_BUSY without touching node.
     b. drained tail (unlocked wire_stop/emit window) -> shutdown_active
        still true until re-acquired near return -> destroy blocked same way.
     c. !drained tail (unlocked emit_monitor_event/complete_operation loop)
        -> same protection.
     d. destroy in progress, shutdown starts concurrently -> destroy merges
        admission check + forced-stop commit under one lock_guard (no gap),
        calls unregister_node before wire_stop/delete. Checked as_mesh_node
        (mesh_runtime.cpp:395-404) validates against a live_nodes registry
        guarded by a *separate* registry mutex — so any call after
        unregister_node gets EFAULT on a NULL lookup, never touching freed
        memory. The narrow window between lock_guard release and
        unregister_node is safe because a shutdown grabbing node->mutex in
        that window would see state==STOPPED and return OK immediately
        without further node access.
   - Read the new test test_destroy_during_shutdown_wait_is_deadlock_error
     (test_mesh_lifecycle_contracts.cpp:569-604): parks shutdown via a held
     claim, confirms parked (300ms + rc==-1), destroy concurrently ->
     CLOSE_BUSY+EDEADLK+node survives, then release+join+destroy succeed.
     This directly exercises interleaving (a) with real concurrency; the
     other 3 are closed by code-structure argument (documented above).
   - Checked errno map ko/en 04-errno-map.{ko.,}md: ZLINK_CLOSE_BUSY row now
     lists EBUSY and EDEADLK with the §11 cross-reference, matching code and
     spec §11 (01-mesh-node.ko.md:506-509) wording exactly.
   - Verdict: RESOLVED.
