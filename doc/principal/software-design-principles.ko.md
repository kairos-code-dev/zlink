# 에이전틱 코딩을 위한 소프트웨어 설계 원칙

> *A Philosophy of Software Design* (John Ousterhout, 2판) 기반  
> AI 에이전트가 코드를 생성·검토·수정할 때 바로 적용할 수 있는 행동 규칙으로 정리한 문서.

---

## 핵심 전제

**소프트웨어 개발에서 근본적인 문제는 복잡성이다.**  
복잡성은 시스템을 이해하기 어렵게 만들고 변경하기 어렵게 만들며 버그를 불러온다.  
모든 설계 결정은 복잡성을 줄이는지 늘리는지를 기준으로 평가해야 한다.

복잡성은 세 가지 증상으로 나타난다:

| 증상 | 설명 |
|---|---|
| **변경 증폭** | 단순한 변경 하나가 여러 곳의 수정을 요구한다 |
| **인지 부하** | 모듈을 이해하거나 사용하려면 너무 많은 것을 알아야 한다 |
| **미지의 미지** | 무엇을 알아야 하는지조차 모른다 — 세 가지 중 가장 위험하다 |

복잡성의 근본 원인은 두 가지다:

- **의존성** — 코드를 독립적으로 이해하거나 변경할 수 없다
- **불명확성** — 중요한 정보가 눈에 보이지 않는다

복잡성은 점진적으로 쌓인다. 단 하나의 큰 원인이 아니라, 수백 개의 작은 추가가 누적된 결과다.  
**사소한 것도 신경 써야 한다.**

## 마인드셋: 전략적으로, 전술적으로가 아니라

### 전술적 프로그래밍의 함정

전술적 프로그래밍: "일단 돌아가게 만들자."  
각 작업마다 복잡성이 조금씩 추가된다. 몇 달이 지나면 코드베이스는 손댈 수 없는 상태가 된다.  
전술적 개발자는 빠르게 보이지만 뒤에 피해를 남긴다.  
"전술적 토네이도" — 빠르고 생산적인 개발자 — 는 관리자에게는 영웅이지만 팀원에게는 악몽이다.

### 전략적 투자

전략적 프로그래밍: "시스템을 확장하기 쉽게 만들자."  
개발 시간의 **10–20%** 를 설계에 투자한다.  
6–18개월 후에는 전술적 방식보다 영구적으로 빠른 개발 속도를 얻는다.

**목표는 동작하는 코드가 아니다. 동작하면서도 잘 설계된 코드가 목표다.**

### 에이전트에게

- 처음 떠오른 구현을 바로 선택하지 않는다. 최소 두 가지 설계를 검토한다.
- 마감을 맞추기 위해 복잡성을 추가하지 않는다. 비용은 복리로 쌓인다 — 나중에 더 많이 치른다.
- 기존 코드를 수정할 때는 조금 더 나은 상태로 남긴다. 작업 중에 발견한 주변의 설계 문제를 함께 고친다.
- 문제를 우회하고 싶은 충동이 들 때는 근본 원인을 찾아 고친다.
- 안전 검사나 추상화를 지름길로 건너뛰지 않는다.

## 깊은 모듈

**이 책에서 가장 중요한 개념이다.**

모듈의 **비용** = 인터페이스 (다른 코드가 배워야 하고 의존해야 하는 것)  
모듈의 **이득** = 구현 (모듈이 실제로 하는 일)  
**이득 대 비용을 최대화하라: 단순한 인터페이스, 강력한 구현.**

```
Deep Module (Good)          Shallow Module (Bad)
┌────────────────┐          ┌──────────────────────────┐
│  simple API    │          │  complex API             │
├────────────────┤          ├──────────────────────────┤
│                │          │  thin implementation     │
│  large, rich   │          └──────────────────────────┘
│  implementation│
│                │
└────────────────┘
```

### 대표적인 예시

| 깊은 모듈 (좋은 예) | 얕은 모듈 (나쁜 예) |
|---|---|
| Unix `open/read/write/close/lseek` — 5개 호출로 모든 I/O 처리 | Java `FileInputStream→BufferedInputStream→ObjectInputStream` |
| 가비지 컬렉터 — 인터페이스 없이 메모리를 조용히 관리 | 모든 필드에 getter와 setter |
| TCP — 패킷 손실·재전송·순서를 숨김 | 아무것도 추가하지 않는 단순 위임 래퍼 |

### 클래시티스 (Classitis)

"클래스가 많을수록 좋은 설계"라는 잘못된 믿음이 **클래시티스**를 만든다: 작고 얕은 클래스가 수없이 많아지는 병이다.  
개별 클래스는 단순하지만 인터페이스 복잡성의 총합은 거대해진다.  
**작은 것이 미덕이 아니다. 깊은 것이 미덕이다.**

### 규칙

- 작은 API 여러 개보다 기능이 강한 API 몇 개를 선호한다.
- 인터페이스가 구현만큼 복잡하다면 그 추상화는 가치가 없다 — 얕은 모듈이다.
- **단순한 인터페이스 > 단순한 구현.** 복잡성은 내부에서 흡수하고 호출자에게는 깔끔한 표면을 제공한다.
- 기본 동작은 설정 없이 일반적인 경우를 처리해야 한다.

## 정보 은닉

각 모듈은 **하나의 설계 결정을 캡슐화**해야 한다 — 호출자에게 완전히 숨겨서.

숨겨야 할 것: 자료구조, 알고리즘, 프로토콜, 파일 형식, 외부 API, 설정 선택.

### 정보 누출 — 가장 흔한 설계 오류

하나의 설계 결정이 여러 모듈에 반영되어 있으면 누출된 것이다.  
**증상:** 하나를 바꾸면 여러 곳을 수정해야 한다.

두 가지 형태의 누출:
- **인터페이스 누출** — 설계 결정이 공개 API에 드러남
- **뒷문 누출** — 두 모듈이 인터페이스 없이 같은 사실을 공유함 (더 나쁨, 눈에 보이지 않기 때문)

### 시간적 분해 — 가장 흔한 함정

정보 소유권이 아니라 실행 순서를 기준으로 코드를 구조화하는 것:

```
// 잘못된 예: Reader, Parser, Writer 모두 파일 형식을 안다
Reader → Parser → Writer

// 올바른 예: 하나의 클래스가 파일 형식 지식 전부를 소유
FileHandler { read(), parse(), write() }
```

"언제 일어나는가"를 기준으로 클래스를 나누지 않는다.  
"어떤 정보를 소유하는가"를 기준으로 나눈다.

### `private` ≠ 정보 은닉

필드를 `private`으로 선언하고 getter·setter를 제공하면 그 필드에 대한 모든 것이 드러난다.  
필드의 타입, 의미, 사용 방식이 접근자 API로 전부 노출된다.  
진정한 정보 은닉은 그 필드의 **존재** 자체가 호출자에게 무관한 것이다.

### 규칙

- 두 모듈이 같은 지식을 공유하면 합치거나 그 지식을 하나의 모듈로 추출한다.
- 각 클래스는 정확히 하나의 응집된 설계 정보를 소유해야 한다.
- 호출자는 모듈이 어떻게 동작하는지가 아니라 무엇을 보장하는지만 알아야 한다.
- 내부 표현을 공개 API에 노출하지 않는다.
- 모든 필드에 기본으로 getter·setter를 추가하지 않는다 — 이것은 정보 은닉의 반대다.
- **가장 좋은 기능은 호출자가 존재조차 모르는 기능이다** (예: 자동 버퍼링). "모듈이 알아서 올바르게 처리한다"가 목표다.

## 범용 모듈

**과도한 특수화는 소프트웨어 복잡성의 단일 최대 원인이다.**  
범용 코드는 특수 목적 코드보다 단순하고 깔끔하며 이해하기 쉽다.

### 적절한 수준: "어느 정도 범용적"

구현은 오늘의 필요를 충족한다.  
**인터페이스**는 여러 용도를 수용할 수 있을 만큼 범용적이다.  
인터페이스를 지금 당장의 특정 사용 사례에 종속시키지 않는다.

### 나쁜 예: 특수화된 인터페이스

```java
// UI에 종속됨 — backspace, delete, deleteSelection이
// 텍스트 클래스를 UI 개념으로 오염시킨다
void backspace(Cursor cursor);
void delete(Cursor cursor);
void deleteSelection(Selection selection);
```

### 좋은 예: 범용 인터페이스

```java
// 범용: 임의 범위의 텍스트에 동작한다
void insert(Position position, String newText);
void delete(Position start, Position end);
Position changePosition(Position position, int numChars);
```

범용 인터페이스는 메서드 수가 *더 적고* 사용하기 *더 쉽다.*  
특수 목적 로직(backspace가 어떤 문자를 지우는지)은 그것이 속한 UI 계층으로 올라간다.

### 범용성을 평가하는 3가지 질문

1. **현재 모든 필요를 만족하는 가장 단순한 인터페이스는 무엇인가?**  
   기능 손실 없이 메서드 수가 적을수록 더 범용적이다.

2. **이 메서드는 몇 가지 다른 상황에서 사용될 것인가?**  
   하나뿐이라면 아마도 너무 특수 목적이다.

3. **이 API는 현재 필요를 위해 사용하기 쉬운가?**  
   상당한 추가 코드가 필요하다면 너무 범용적(기능이 부족)일 수 있다.

### 특수화를 위로 (또는 아래로) 밀어내라

- 특수 목적 코드는 그것이 필요한 가장 높은 계층에 두어야 한다 (예: UI 전용 로직은 UI에 남긴다).
- 또는 범용 인터페이스를 구현하는 드라이버·어댑터 계층으로 아래로 밀어낸다.
- 특수 목적 관심사가 하위 범용 모듈로 새어 들어오게 두지 않는다.

### 코드에서 특수 경우를 제거하라

특수 경우는 설계 선택의 결과로만 존재하는 `if` 문이다.  
개념을 재정의하면 특수 경우 자체가 사라지는 경우가 많다:

- 대신에: "selection이 null일 수 있으니 사용 전에 확인"  
  이렇게: "selection은 항상 존재한다; 아무것도 선택되지 않았으면 빈 범위(start == end)다"

특수 경우가 없는 코드는 더 단순하고 더 명확하며 버그도 적다.

### 규칙

- 새 모듈을 작성할 때 인터페이스를 현재 필요보다 더 범용적으로 만든다.
- 비슷한 일을 하는 특수 목적 메서드가 세 개 있다면, 세 가지를 모두 처리하는 범용 메서드 하나를 찾는다.
- 범용성 검증: 수정 없이 두 번째 사용 사례를 처리할 수 있는가?
- 특수 목적 로직을 그것이 필요한 가장 높은 계층으로 올린다.
- 일반 경로가 엣지를 처리하도록 개념을 재정의해서 코드에서 특수 경우를 제거한다.

## 복잡성을 아래로 끌어내려라

피할 수 없는 복잡성이 있다면, 모듈 개발자가 흡수해야 한다 — 호출자가 아니라.

> "100명의 호출자가 겪는 고통은 개발자 한 명의 추가 노력보다 더 나쁘다."

### 설정 파라미터의 함정

설정 파라미터를 노출하는 것은 종종 어려운 문제를 풀기 싫어서 회피하는 방식이다.  
파라미터를 노출하기 전에, 호출자가 모듈이 접근할 수 없는 정보를 실제로 갖고 있는지 확인한다.  
모듈이 스스로 올바른 값을 관찰하고 계산할 수 있다면 (예: 왕복 시간을 측정해서 재시도 간격 설정), 직접 해야 한다 — 사용자에게 설정하도록 요구하지 않는다.

### 규칙

- 합리적인 기본값을 제공한다. 일반적인 경우는 설정 없이 동작해야 한다.
- 호출자가 처리해야 하는 특수 경우를 모듈이 처리할 수 있다면 아래로 끌어내린다.
- 모듈이 조용히 올바르게 처리할 수 있는 것에 대해 예외를 던지지 않는다.
- 호출자가 모듈 내부에 속하는 사전·사후 단계를 수행하도록 요구하지 않는다.
- 각 모듈은 자신의 문제를 완전히 해결해야 한다. 설정 파라미터는 해결이 불완전하다는 신호다.

## 다른 계층, 다른 추상화

인접한 계층은 같은 추상화를 가져서는 안 된다. 같다면 그 중 하나는 불필요하다.

### 패스스루 메서드

패스스루 메서드는 같은 시그니처를 가진 다른 메서드를 호출하는 것 외에 아무것도 하지 않는다:

```java
// TextDocument.insertString은 TextArea.insertString만 호출 — 추가되는 것이 없다
public void insertString(String text, int offset) {
    textArea.insertString(text, offset);
}
```

이것은 클래스 간 책임 경계가 불분명하다는 증상이다.

**해결 방법 (우선순위 순):**
1. 상위 클래스를 없애고 하위 클래스를 호출자에게 직접 노출한다
2. 클래스 간 기능을 재분배한다
3. 두 클래스를 합친다

### 패스스루 변수

소비자 하나에게 도달하기 위해 많은 메서드 시그니처를 통과하는 변수.  
**해결 방법:** 컨텍스트 객체 사용 — 전역 상태를 한 곳에 저장하고 생성 시점에 컨텍스트를 한 번만 전달한다.

### 데코레이터

데코레이터는 같은 API로 기존 객체를 확장한다.  
문제점: 데코레이터는 얕아지기 쉽다 (얇은 래퍼, 많은 패스스루 메서드).

데코레이터를 만들기 전에 아래 대안을 순서대로 검토한다:
1. **기반 클래스에 직접 추가** — 기능이 범용적이고 대부분의 호출자가 사용한다면
2. **사용 사례와 합침** — 기능이 하나의 컨텍스트에만 필요한 특수 목적이라면
3. **기존 데코레이터와 합침** — 두 개의 얕은 데코레이터보다 하나의 깊은 데코레이터가 낫다
4. **독립 클래스로 구현** — 기능이 래핑을 필요로 하지 않는다면

래핑 클래스를 수정할 수 없고 인터페이스 적응이 필요한 경우에만 데코레이터를 사용한다.

### 인터페이스 대 구현

내부 표현이 인터페이스와 일치한다면 (둘 다 라인 단위, 둘 다 바이트 단위), 그 클래스는 얕다 — 아무것도 숨기지 않는다.  
클래스의 가치는 정확히 **인터페이스와 구현 사이의 간극**이다.

### 규칙

- 각 계층은 아래 계층이 제공하지 않는 것을 변환하거나 제공해야 한다.
- 클래스가 다른 클래스에만 위임한다면, 합치거나 위임자를 제거한다.
- 변수가 소비자에 도달하기 위해 4개 이상의 함수 시그니처를 통과하면 컨텍스트 객체를 사용한다.

## 함께가 나은가, 분리가 나은가

### 코드가 함께 있어야 한다는 신호

- **같은 정보를 공유한다** (둘 다 파일 형식을 알거나, 둘 다 프로토콜 세부 사항을 안다)
- **항상 함께 사용된다** — 관계가 양방향이다
- **개념적으로 겹친다** — 자연스러운 상위 범주가 둘을 포괄한다
- **하나를 이해하려면 다른 하나를 읽어야 한다**

### 합쳐야 할 때

- 합침으로써 **정보 누출이 제거된다** (공유 지식이 한 곳에)
- 합침으로써 **인터페이스가 단순해진다** (호출자 입장에서 메서드·파라미터 수 감소)
- 합침으로써 **비자명한 로직의 중복이 제거된다**

### 분리해야 할 때

- 범용 코드와 특수 목적 코드가 **섞여 있다** — 분리한다
- 두 부분이 **공유하는 정보도 없고 의존성도 없다**

### 메서드 분리: 길이가 아니라 깊이

**메서드가 길다는 이유만으로 분리하지 않는다. 더 명확한 추상화가 만들어질 때만 분리한다.**

분리는 복잡성을 추가한다: 인터페이스 증가, 간접 참조 증가, 읽을 때 문맥 전환 증가.  
단순한 인터페이스를 가진 100줄 메서드가 함께 읽어야 하는 5개의 20줄 메서드보다 낫다.

**분리해야 할 때:**
- 하위 작업이 명확히 분리 가능하고 추출한 메서드가 단독으로 의미를 갖는다
- 추출한 메서드가 다른 호출자에서도 사용될 만큼 범용적이다
- 분리 후 부모와 자식을 **서로 없이도 이해**할 수 있다

**분리하지 말아야 할 때:**
- 호출자가 두 절반을 순서대로 호출해야 한다 (복잡성이 위로 올라간다)
- 두 절반이 너무 많은 상태를 공유해서 함께만 이해할 수 있다 ("결합된 메서드")
- 결과가 구현보다 인터페이스가 더 많은 얕은 메서드가 된다

> **"깊이가 길이보다 중요하다. 깊이를 길이와 바꾸지 않는다."**  
> "모든 함수는 작아야 한다" (Clean Code)는 메서드 수준의 클래시티스를 만든다.

### 규칙

- "크다"는 이유만으로 클래스를 나누지 않는다. 두 가지 별개의 정보를 담고 있을 때 나눈다.
- 독립적으로 이해 가능하고 여러 호출자가 있거나 있을 가능성이 있을 때만 헬퍼 메서드를 만든다.
- 반복되는 비자명한 로직은 항상 추출 신호 — 그러나 **깊은** 함수로 추출한다, 얕은 것이 아니라.
- 긴 메서드를 나누기 전에 자문한다: "각 부분을 독립적으로 이해할 수 있는가?" 아니라면 함께 둔다.

## 오류 처리: 오류를 존재하지 않게 정의하라

예외 처리는 복잡성의 최악의 원인 중 하나다.  
목표는 **예외를 처리해야 하는 장소의 수를 최소화**하는 것이다.

### 선호 순서대로 나열한 네 가지 전략

| 전략 | 사용 시점 | 예시 |
|---|---|---|
| **정의로 없애기** | API 의미를 재정의해서 그 조건이 더 이상 오류가 아니게 만든다 | `unset x`는 `x`가 없어도 성공한다; `substring`은 겹치는 범위를 반환한다 |
| **예외 마스킹** | 내부에서 처리; 호출자는 볼 수 없다 | TCP는 손실 패킷을 투명하게 재전송한다; NFS는 서버가 복구될 때까지 재시도한다 |
| **예외 집약** | 최상위의 핸들러 하나가 관련 오류 전부를 잡는다 | 웹 서버의 최상위 디스패처가 누락 파라미터 오류를 한 곳에서 처리한다 |
| **크래시** | 복구 불가; 계속 실행하면 더 나쁘거나 무의미하다 | 메모리 부족; 내부 불변 조건 위반 |

### 규칙

- 예외를 던지기 전에 묻는다: "이 상황이 오류가 아니도록 이 연산을 재정의할 수 있는가?"
- 호출자가 합리적으로 다르게 처리할 수 없는 조건에 대해 예외를 던지지 않는다.
- 세분화된 예외 타입을 여러 개 노출하지 않는다. 의미 있는 경계에서 집약한다.
- 전파되어야 하는 오류는 최상위에서 한 번 잡는다 — 모든 중간 계층마다 잡지 않는다.
- "모든 것을 감지하고 던져라"는 방어적 프로그래밍이 아니다 — 복잡성 증폭이다.
- 예외가 많은 클래스는 얕은 클래스다. 예외는 인터페이스 비용의 일부다.

## 두 번 설계하라

모든 중요한 설계 결정에서 **근본적으로 다른 두 가지 접근 방식** 이상을 검토한다.

### 이유

- 첫 번째 아이디어가 최선인 경우는 드물다.
- 대안을 비교하면 무엇이 중요한지 명확히 말할 수 있게 된다: 단순성, 범용성, 성능.
- 한 대안이 나쁜 이유를 발견하면 좋은 설계가 무엇을 요구하는지 배우게 된다.
- 영리한 사람일수록 이 단계를 건너뛰기 쉽다 — "처음에 올바르게 할 것이다"가 함정이다.
- 아무리 뛰어난 사람도 결국 첫 번째 접근으로는 너무 어려운 문제를 만난다.

### 방법

1. 두세 가지 접근 방식을 **인터페이스 수준**에서 스케치한다 — 완전히 구현하지 않는다.
2. 각각의 장단점을 나열한다: 단순성, 범용성, 효율성, 호출자 부담.
3. 최선을 선택하거나, 비교에서 배운 것으로 새로운 설계를 합성한다.

이것은 모든 수준에 적용된다: API 형태, 모듈 분해, 오류 전략, 자료구조 선택.

### 규칙

- 비자명한 모듈의 첫 줄을 작성하기 전에 인터페이스 설계 두 가지를 초안으로 작성한다.
- 첫 번째 설계가 명백히 맞는 것처럼 느껴져도 의도적으로 대안 하나를 만든다.
- 선택한 설계를 선택한 이유를 문서화한다 (주석이나 PR 설명에 한 문장).

## 이름 짓기

이름은 인지 부하를 줄이는 1차 도구다.  
이름은 추상화다: "대략 맞다"가 아니라 대상의 본질을 전달해야 한다.

### 핵심 규칙

- 이름은 선언부나 문서를 보지 않아도 **정확한 심상**을 만들어야 한다.
- **구체적인 것**을 **포괄적인 것**보다 선호한다: `count` 대신 `numActiveConnections`; `pos` 대신 `nextWriteOffset`.
- 좋은 이름을 찾을 수 없다면 설계가 잘못되어 있을 가능성이 높다 — 개념 자체가 불명확한 것이다.
- **같은 개념 → 같은 이름**, 모든 곳에서, 항상. 같은 것을 가리키는 유의어를 쓰지 않는다.
- **다른 개념 → 다른 이름.** 두 가지 다른 것에 같은 이름을 재사용하지 않는다 (`block` 버그).
- 정보를 추가하지 않는 단어를 제거한다: `fileObject` → `file`, `setValueOfField` → `setField`.

### 일관성 — 세 가지 요건

1. 특정 목적에는 항상 공통 이름을 사용한다.
2. 그 공통 이름을 다른 목적에는 절대 사용하지 않는다.
3. 목적이 충분히 좁아서 그 이름을 공유하는 모든 변수의 동작이 동일해야 한다.

요건 3의 위반이 파일 시스템 버그를 만들었다: `block`이 물리적 블록과 파일 블록 두 가지를 의미했다. 하나가 필요한 곳에 다른 하나가 쓰였다.

### 거리 규칙

이름의 선언부와 사용처가 멀수록 이름은 길어야 한다.  
짧은 루프 변수명 (`i`, `j`)은 루프 전체가 화면에 들어올 때 괜찮다.  
선언부와 사용처를 동시에 볼 수 없다면, 더 길고 서술적인 이름을 사용한다.

### 이름이 너무 구체적일 수도 있다

텍스트 범위를 삭제하는 메서드의 인자 이름이 `selection`이면, 현재 UI 선택 항목이어야 한다는 암시를 준다. 그러나 그 메서드는 임의의 범위에서 동작한다. `range`를 사용한다.  
이름의 과도한 구체성은 제약에 대한 잘못된 가정을 만든다.

### 나쁜 패턴

| 나쁜 예 | 좋은 예 | 이유 |
|---|---|---|
| `tmp`, `data`, `info` | 구체적인 이름 | 아무것도 전달하지 않는다 |
| `handleStuff` | `retransmitLostPacket` | 동작을 정확하게 이름 짓는다 |
| `flag`, `flag2` | `isConnected`, `hasError` | 불리언은 술어여야 한다 |
| `block` (두 가지에 사용) | `fileBlock`, `diskBlock` | 같은 이름, 다른 동작 = 버그 |

## 주석

주석은 **코드가 말할 수 없는 것**을 기록한다 — 코드가 이미 말하는 것이 아니라.

### 주석을 달아야 할 것

- **왜**, 무엇이 아니라: 설계 결정, 제약, 비자명한 불변 조건, 트레이드오프
- **인터페이스 계약**: 호출자가 제공해야 할 것, 피호출자가 보장하는 것, 단위, null 의미론, 오류 조건, 부작용
- **놀라운 동작**: 유능한 독자가 처음 읽을 때 틀릴 수 있는 모든 것

### 주석을 달지 말아야 할 것

- 코드 자체에서 바로 알 수 있는 것
- 인터페이스 수준 주석에 구현 세부 사항
- 코드를 산문으로 되풀이하는 것

### 주석 먼저 설계하기

인터페이스 주석을 구현보다 **먼저** 작성한다.

새 클래스를 만드는 절차:
1. **클래스 인터페이스 주석**을 먼저 작성한다
2. **공개 메서드 시그니처 + 인터페이스 주석**을 작성한다 (본문은 아직 없다)
3. 추상화가 올바르게 느껴질 때까지 반복한다
4. **인스턴스 변수 선언 + 주석**을 작성한다
5. **메서드 본문**을 채운다, 필요에 따라 구현 주석을 추가한다

주석 작성이 어렵다면 인터페이스가 이해하기 어렵다는 뜻 — 다시 설계한다.  
단순한 메서드에 길거나 모호한 주석이 필요하다면 추상화가 잘못되었다는 신호다.  
**주석은 복잡성을 알리는 광산의 카나리아다.**

### 주석은 코드에 있어야 한다, 커밋 로그가 아니라

커밋 메시지는 거의 읽히지 않는다. 커밋 로그에만 있는 중요한 정보는 사라진다.  
미래의 개발자가 어떤 결정이 왜 내려졌는지 이해해야 한다면, 코드 옆의 주석에 넣는다.  
커밋 메시지에 사본을 두는 것은 괜찮지만 **코드가 정본이다**.

### 중복 없이

각 설계 결정은 정확히 한 곳에 문서화해야 한다.  
사실이 여러 위치에서 관련이 있다면, 한 곳에 문서화하고 다른 곳에는 참조를 추가한다:  
`// 이 제약의 설명은 Foo.bar의 주석을 참조.`

마스터 주석이 이동해서 참조가 끊어지면, 끊어진 것이 즉시 보인다. 중복된 주석이 어긋나면 아무런 신호도 없다.

### 규칙

- 코드를 되풀이하는 주석을 작성하지 않는다.
- 인터페이스 주석은 **호출자 관점**에서 동작을 설명한다.
- 설계 결정이 비자명하면 "왜" 한 줄 주석을 추가한다.
- 코드를 수정한 후, 인접 주석이 새로운 동작을 여전히 정확하게 설명하는지 확인한다.
- 공개 API의 인터페이스 주석 누락을 리뷰 문제로 표시한다.

## 코드 명확성

코드는 작성하는 것보다 읽히는 횟수가 훨씬 많다. **작성자가 아닌 독자를 위해 최적화한다.**

### 명확성 기법

- **빈 줄**로 논리적 블록을 분리한다; 각 블록 앞에 간략한 주석을 달아 둔다.
- 선언 타입을 실제 타입과 일치시킨다 (`ArrayList`를 할당하면서 `List`로 선언하지 않는다).
- 범용 컨테이너 (`Pair<A, B>`)를 사용하지 않는다 — 의미 있는 필드명을 가진 명명된 구조체를 정의한다.
- 독자의 기대를 따른다: 생성자가 스레드를 시작한다면 주석에 눈에 띄게 명시한다.
- 이벤트 기반 흐름 제어는 꼭 필요할 때만 사용한다; 사용할 때는 각 핸들러가 언제 실행되는지 정확히 주석으로 남긴다.

### 일관성

하나의 관례를 선택하고 모든 곳에 적용한다.  
**로컬 관례를 "개선"하지 않는다.** 일관성이 로컬 완벽함보다 중요하다.  
기존 관례가 잘못되었다면, 모든 곳에서 바꾸거나 그냥 두어라 — 비일관적으로 만들지 않는다.

### 불변 조건

**불변 조건**은 변수나 자료구조에서 항상 참인 속성이다.  
예: "텍스트 버퍼의 모든 줄은 개행 문자로 끝난다."

불변 조건은 가장 강력한 일관성 도구 중 하나다:

- 불변 조건은 자료구조의 모든 사용처를 한 번에 추론할 수 있게 해준다 — 불변 조건이 배제하는 엣지 케이스를 확인하는 코드가 필요 없다.
- 불변 조건이 성립하면, 그것이 제거하는 코너 케이스를 위한 특수 경우 코드 자체가 사라진다.
- 불변 조건은 하나의 모듈 안에서 강제한다; 호출자가 위반하도록 두지 않는다.

불변 조건은 정보 은닉의 한 형태다: 코너 케이스가 존재할 수 없다는 사실이 모듈 내부에 숨겨진다.

## 기존 코드 수정하기

전략적 마인드셋은 새 코드와 마찬가지로 수정에도 적용된다.

### 전략적으로 유지하기

기존 코드를 변경할 때 목표는 가장 작은 변경이 아니다.  
목표는: **변경이 끝났을 때 시스템이 처음부터 이 변경을 염두에 두고 설계된 것처럼 보여야 한다.**

"최소 패치" 본능에 저항한다. 최소 패치 하나하나가 특수 경우, 의존성, 간접 참조 계층을 추가한다. 많은 패치가 쌓이면 설계는 영구적으로 퇴화한다.

### 주석 위생

- **주석을 설명하는 코드 옆에 함께 둔다.** 코드와 멀리 떨어진 주석은 코드가 변경되어도 업데이트되지 않는다.
- 주석은 헤더 파일이 아니라 구현 파일(`.c`, `.cpp`)의 코드 옆에 둔다. 구현을 편집하는 개발자는 볼 수 있지만 헤더만 편집하는 개발자는 보지 못한다.
- 하위 단계 주석은 메서드 상단이 아니라 각 하위 단계 바로 위에 둔다.
- 주석이 추상적일수록 유지하기 쉽다 — 코드 세부 사항이 아닌 전체 의도만 추적한다.

### 커밋 전 diff 확인

커밋하기 전에 변경된 모든 줄을 훑어본다.  
인접 주석이 새로운 동작을 여전히 정확하게 반영하는지 확인한다.  
실수로 남긴 디버그 코드, 미해결 TODO, 오타도 함께 잡는다.

### 규칙

- 코드에 손을 댈 때는 조금 더 나은 상태로 남긴다. 작업 중 발견한 주변의 작은 문제를 고친다.
- 설계 문제를 발견했지만 지금 고칠 수 없다면, 나중에 처리할 수 있을 만큼의 맥락을 담은 TODO 주석을 추가한다.
- 주석은 코드에 있어야 한다. 커밋 로그 문서화를 코드 수준 문서화의 대체물로 사용하지 않는다.
- 각 설계 결정: 한 곳에 문서화하고 다른 곳에서는 참조한다.

## 성능

**단순하고 깊은 코드는 복잡하고 얕은 코드보다 더 빨리 실행되는 경향이 있다.**

이것은 우연이 아니다: 복잡한 코드는 대개 중복되거나 불필요한 작업을 하고 얕은 계층은 이득 없이 오버헤드를 추가한다.  
단순성을 위한 설계와 성능을 위한 설계는 같은 방향으로 향한다.

### 성능이 문제가 될 때

- 모든 곳에서 마이크로 최적화하지 않는다. **임계 경로** — 가장 일반적인 경우에 실행되는 코드 — 를 파악하고 거기서 최적화한다.
- 수정하기 전에 측정한다. 병목에 대한 개발자의 직관은 경험 많은 개발자조차 신뢰할 수 없다.
- 임계 경로에서 특수 경우 확인을 최소화한다. 이상적으로는 상단의 단일 확인이 모든 엣지 케이스를 걸러내고 빠른 경로는 추가 분기 없이 실행된다.
- 최적화 후 다시 측정한다. 변경이 측정 가능한 개선을 만들지 않았다면 되돌린다 — 아무것도 얻지 못하는 복잡성은 유지하지 않는다.

### 최적화 전략으로서의 단순성

알고리즘 최적화를 선택하기 전에 먼저 묻는다: "이 코드를 먼저 더 단순하게 만들 수 있는가?"  
얕은 계층 제거, 중복 확인 제거, 불변 조건 강제 — 이것만으로 알고리즘 변경 없이 1.5–2배 속도 향상을 얻는 경우가 많다. 결과는 더 복잡해지는 것이 아니라 더 단순해진다.

## 중요한 것을 결정하라

좋은 설계는 중요한 것과 그렇지 않은 것을 분리하고 중요한 것을 중심으로 시스템을 구성한다.

### 레버리지를 찾아라

**하나의 결정이 많은 문제를 해결**하거나 **하나의 지식이 많은 동작을 설명**하는 설계 선택을 찾는다.

예시:
- 범용 `insert/delete` 텍스트 API는 백스페이스, 삭제, 붙여넣기, 검색·교체를 처리한다 — 레버리지가 높다.
- `backspace()` 메서드는 백스페이스만 처리한다 — 레버리지가 낮다.
- 자료구조의 불변 조건은 그 모든 사용처를 한 번에 추론하게 해준다.

**레버리지가 클수록 더 중요하고 설계에서 더 눈에 띄어야 한다.**

### 중요한 것을 최소화하라

중요한 것이 적을수록 = 더 단순한 시스템.
- 파라미터를 최소화한다: 일반적인 경우에 동작하는 기본값을 선택한다.
- 숨길 수 있는 것은 숨긴다: 모듈이 내부적으로 처리할 수 있다면 호출자는 그 존재를 알 필요가 없다.
- 노출해야 하는 것은 집약한다: 예외를 여러 곳이 아닌 한 곳에서 처리한다.

### 중요한 것을 강조하라

중요한 것을 파악했다면 눈에 보이게 만든다:
- **두드러짐**: 인터페이스, 이름, 눈에 띄는 파라미터에 넣는다 — 옵션 속에 묻지 않는다.
- **중심성**: 가장 중요한 것이 주변 구조를 형성해야 한다, 세부 사항이 되어서는 안 된다.

### 두 가지 실패 모드

| 실패 | 증상 | 결과 |
|---|---|---|
| **너무 많은 것을 중요하게 취급** | 호출자가 볼 수 있는 파라미터 다수, 얕은 클래스, 과도한 설정 | 인지 과부하, 복잡성 |
| **중요성을 인식하지 못함** | 숨겨진 핵심 정보, 누락된 필수 기능 | 미지의 미지, 버그, 중복 우회책 |

### 규칙

- 묻는다: "이 설계 결정은 레버리지가 높은가 — 이것을 이해하면 다른 많은 것을 설명할 수 있는가?"
- 레버리지가 높은 결정은 눈에 띄는 위치에 둔다: 인터페이스 이름, 최상위 추상화.
- 레버리지가 낮은 세부 사항은 구현 내부에 숨긴다.
- 거의 필요 없는 세부 사항을 모든 호출자에게 노출하고 있다면, 아래로 끌어내리거나 선택적으로 만든다.

## 테스트 커버리지 기본 기준

테스트는 설계의 일부다. 테스트는 동작을 명확하게 만들고, 계약이 시간이 지나며
어긋나는 것을 막으며, 이후 변경에서 추측 없이 복잡성을 줄일 수 있게 해준다.

기본 목표 커버리지는 **라인 커버리지 80%**다. 이 숫자는 기준선이며 판단을
대체하지 않는다:

- 커버리지는 공개 계약, 프로토콜 호환성, 생명주기 경계, 오류 경로, timeout/abort
  동작, backpressure, 샘플 회귀 테스트를 우선해야 한다.
- 커버리지 숫자가 높아도 사용자가 보는 중요한 동작이 빠져 있으면 품질을 증명하지
  못한다.
- 80% 아래로 내려가려면 생성 코드, 플랫폼별 연결 코드, 통합 테스트나 계약 테스트가
  더 적합한 코드처럼 명확한 이유가 있어야 한다.
- 비율을 올리기 위한 얕은 테스트를 추가하지 않는다. 테스트는 의미 있는 동작을
  설명하고 이후 변경 위험을 줄여야 한다.

모듈이 공개 API나 언어 간 계약을 노출한다면 구현 세부 사항을 넓게 고정하는 테스트보다
초점이 분명한 계약 테스트를 우선한다. 목표는 모듈의 보장을 지키면서도 구현은 쉽게
리팩토링할 수 있게 두는 것이다.

## 위험 신호 체크리스트

코드를 생성하거나 검토할 때 아래 경고 신호를 확인한다.  
각 신호는 복리로 쌓이는 설계 부채를 나타낸다.

| # | 위험 신호 | 진단 질문 |
|---|---|---|
| 1 | **얕은 모듈** | 인터페이스를 배우는 비용이 구현이 절약해 주는 비용만큼 드는가? |
| 2 | **정보 누출** | 같은 설계 결정이 여러 모듈에 반영되어 있는가? |
| 3 | **시간적 분해** | 구조가 정보 소유권이 아닌 실행 순서를 기반으로 하는가? |
| 4 | **과도한 노출** | 일반적인 기능을 사용하려면 거의 쓰이지 않는 기능도 알아야 하는가? |
| 5 | **패스스루 메서드** | 메서드가 인자를 전달하는 것 외에 다른 일을 하는가? |
| 6 | **반복** | 같은 비자명한 로직이 여러 곳에 나타나는가? |
| 7 | **특수-범용 혼합** | 특수 목적 로직이 범용 로직과 엉켜 있는가? |
| 8 | **결합된 메서드** | 메서드 A를 이해하려면 메서드 B를 읽어야 하는가? |
| 9 | **주석이 코드를 반복** | 주석이 코드가 이미 말하는 것과 정확히 같은 말을 하는가? |
| 10 | **인터페이스 주석에 구현 노출** | 인터페이스 주석이 구현 세부 사항을 드러내는가? |
| 11 | **모호한 이름** | 이름이 정확한 심상을 만들지 못하는가? |
| 12 | **이름 짓기 어려움** | 좋은 이름을 찾기 어려운가? (개념 자체가 불명확할 수 있다) |
| 13 | **설명하기 어려움** | 인터페이스 주석이 길어야 하는가? (인터페이스가 너무 복잡할 수 있다) |
| 14 | **비자명한 코드** | 유능한 독자가 한눈에 코드의 동작을 이해할 수 있는가? |

## 설계 원칙 요약

1. 복잡성은 점진적으로 쌓인다 — 사소한 것도 신경 써야 한다.
2. 동작하는 코드만으로는 충분하지 않다. 장기를 위해 설계한다.
3. 작은 설계 개선에 지속적으로 투자한다.
4. **모듈은 깊어야 한다** — 단순한 인터페이스 뒤에 강력한 기능.
5. 가장 일반적인 사용 사례를 먼저 위한 인터페이스를 설계한다.
6. **단순한 인터페이스 > 단순한 구현.**
7. **범용 모듈이 더 깊다** — 과도한 특수화는 복잡성의 가장 큰 원인이다.
8. 범용 코드와 특수 목적 코드를 분리한다; 특수화를 가장자리로 밀어낸다.
9. 다른 계층은 다른 추상화를 가져야 한다.
10. **복잡성을 아래로 끌어내린다** — 모듈 개발자가 고통을 감수해서 호출자가 겪지 않도록.
11. 가능한 곳에서 **오류를 정의로 없앤다**.
12. **두 번 설계한다** — 항상 최소 하나의 대안을 비교한다.
13. 주석은 코드가 말할 수 없는 것을 설명한다 — 이미 말하는 것이 아니라.
14. 소프트웨어는 **작성하기 위해서가 아니라 읽히기 위해** 설계되어야 한다.
15. 증분 개발의 단위는 기능이 아니라 **추상화**다.
16. **중요한 것을 결정한다.** 강조한다. 중요하지 않은 것은 최소화하고 숨긴다.
17. 기본 테스트 커버리지 목표는 **80%**다. 다만 원시 비율보다 계약과 위험 경로
    커버리지가 더 중요하다.

---

> "좋은 설계는 소프트웨어를 더 빠르게 개발하게 하고 더 즐겁게 작업하게 만든다.  
> 투자는 돌아온다 — 생각보다 빨리."
