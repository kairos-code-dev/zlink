# zlink 문서화 전면 개편 계획 (코어 가이드 재구조화 + 언어별 바인딩 가이드)

> 성격: 이 문서는 구현 로그가 아니라, zlink 사용자 문서(`doc/guide/`)를 두 축으로
> 다시 세우는 **실행 기준 계획서**다. 두 축은 다음과 같다.
>
> 1. **기존 코어 C 가이드 재구조화** — `doc/guide/`(개념 + C API)를 Diátaxis
>    4분할과 zguide식 점진 순서로 재배치한다.
> 2. **언어별 바인딩 가이드 신설** — `doc/guide/bindings/<lang>`를 고정
>    스켈레톤으로 삼아 7개 언어에 일관되게 작성한다(현재 `dotnet` 시범 초안만 있다).
>
> source of truth:
> - 개념/의미: `doc/guide/`(코어, 언어중립)
> - 바인딩 계약: `doc/spec/bindings/` 및 `core/include/zlink.h`
> - 미러/회귀 제약: `doc/site/docs/`, `DocumentationRegressionTests`
>
> 핵심 원칙: **개념은 한 번만 쓴다.** 같은 설명이 코어 가이드와 언어 가이드,
> 또는 언어 가이드 7벌에 중복되면 드리프트의 원천이 된다. 각 문서 레이어는
> 자기 소유물만 쓰고 나머지는 링크한다.

## 0. 배경과 문제 진단

zlink는 C 코어에 7개 래퍼 바인딩(cpp, dotnet, go, java, node, python, rust)을
얹은 **다국어 메시징 라이브러리**다. 현재 사용자 문서의 상태는 이렇다.

- 코어 가이드(`doc/guide/`)는 16개 문서가 `01~12` 평면 번호로 깔려 있고,
  튜토리얼·개념·how-to·레퍼런스 4가지 성격이 한 챕터 안에 섞여 있다.
- 언어별 사용 가이드는 **사실상 없다.** `doc/guide/bindings/dotnet.ko.md`
  시범 초안 하나만 있다.
- 언어별 계약 청사진(`doc/spec/bindings/<lang>`)과 생성형 API 레퍼런스
  진입점(`bindings/<lang>/README.<tool>.md`)은 7개 언어에 이미 있다.

핵심 문제:
1. **코어 가이드 계층 역전** — 저수준 레퍼런스(routing-id, message ownership,
   socket-options)가 상위 서비스(SPOT/Actor/Registry)보다 뒤에 있다. 특히
   routing-id는 ROUTER/STREAM이 전제하는데도 한참 뒤(08)에 있다.
2. **튜토리얼 부재** — 처음부터 끝까지 따라 만드는 글이 없다.
3. **언어 사용자 진입로 부재** — 각 언어 사용자는 "내 언어 API를 어떻게 쓰나"가
   궁금한데, 그 문서가 dotnet 외엔 없다.

## 1. 목표와 비목표

### 목표
- 코어 가이드를 **목적별로 진입 가능한 구조**(배우기 / 찾기 / 패턴 적용)로 재배치한다.
- 7개 언어가 **동일한 골격·동일한 예제 시나리오**를 공유하는 바인딩 가이드를 확보한다.
- 5개 문서 레이어의 **소유 경계를 명문화**해 중복과 드리프트를 구조적으로 차단한다.
- 신규 언어 추가 시 따라 채우기만 하면 되는 **언어 중립 템플릿**을 제공한다.

### 비목표
- 코어 가이드 내용 **전면 재집필**이 아니다. 재배치 + 그룹핑 + 튜토리얼 1개 신설이 골자다.
- `doc/spec/bindings/`(계약 청사진)는 이 계획의 변경 대상이 아니다. 가이드가
  계약을 따라가는 방향이며, 계약을 가이드에 맞춰 바꾸지 않는다.
- 생성형 API 레퍼런스(docfx/javadoc 등) 자체는 손대지 않는다. 가이드가 거기로 링크만 한다.

## 2. 문서 레이어 모델 (소유 경계)

언어별로 이미 있거나 신설할 문서는 5겹이다. 각 레이어는 **자기 소유물만
작성하고 나머지는 링크**한다. 이것이 이 계획 전체를 관통하는 규칙이다.

| 레이어 | 위치 | 성격(Diátaxis) | 소유물 | 대상 독자 |
|--------|------|---------------|--------|----------|
| 개념 / 왜 | `doc/guide/` (코어) | 설명 + 튜토리얼 | 소켓 패턴, 트랜스포트, 서비스, routing-id 개념 — **언어중립, 1번만** | 전체 |
| 언어별 사용법 | `doc/guide/bindings/<lang>` | how-to + 튜토리얼 | 설치, 관용 예제, **C개념↔언어타입 매핑**, 언어 고유 규칙 | 그 언어 사용자 |
| 심볼 레퍼런스 | `bindings/<lang>` 생성문서 | 레퍼런스 | 모든 타입·멤버 (자동 생성) | 그 언어 사용자 |
| 계약 / 청사진 | `doc/spec/bindings/<lang>` | (내부) | 공개 계약, 시그니처, 정렬 타깃 | 메인테이너·리뷰어 |
| 상위 framework | `framework/languages/<lang>` | 전체 묶음 | DI/handler 등 상위 제품 (현재 dotnet만) | framework 사용자 |

**언어별 사용 가이드의 황금률**:
- 개념은 ↑(코어 가이드)로 링크 — "DEALER란?"을 가이드에 쓰지 않는다.
- 심볼 전체 목록은 ↓(생성문서)로 링크한다.
- 계약은 옆(spec/bindings)으로 링크한다.
- 자기가 직접 소유하는 건 **매핑표 + 그 언어에서만 다른 부분**뿐이다.

## 3. Part A — 코어 C 가이드 재구조화

### 3.1 적용 모델
- **Diátaxis**: 최상위를 튜토리얼 / 개념 / how-to / 레퍼런스로 분할한다.
- **zguide**: 메시징 패턴을 문제·패턴 우선의 점진 순서로 두고, routing-id를 앞세운다.
- **Redis/Stripe**: 이미 좋은 챕터 템플릿(`개요→사용→옵션→패턴→주의`)을 명문화해 유지한다.

### 3.2 목표 구조

```
Part 0 · 시작하기 (Tutorial)
  └─ NEW: 첫 메시징 앱 — DEALER/ROUTER req-rep 끝까지 따라하기
          (01-overview §7 빠른시작을 독립 문서로 승격·확장)

Part 1 · 개념 (Explanation)
  ├─ 개요 & 아키텍처            (01, 빠른시작 절 분리)
  ├─ 소켓 패턴 선택 가이드       (03-0)
  ├─ 메시지 모델 — ownership/zero-copy  (09의 개념 절)
  ├─ 신뢰성·전달 보장 의미       (NEW, 9.2)
  ├─ 설계 근거(왜)              (NEW, 9.3)
  └─ 스레드 안전성 모델          (11)

Part 2 · 메시징 패턴 (How-to, zguide식 점진 순서)
  ├─ Routing ID 기초   (08 → ROUTER 앞으로 이동 ★)
  ├─ PAIR (03-1) → PUB/SUB (03-2) → DEALER (03-3) → ROUTER (03-4)
  ├─ STREAM (03-5)
  └─ Proxy (03-6)

Part 3 · 전송 & 보안 (How-to)
  ├─ Transports (04)
  └─ TLS/보안   (05)

Part 4 · 서비스 계층 (How-to, 상위)
  └─ 서비스 개요(07-0) → Discovery(07-1) → SPOT(07-3) → Actor(07-4) → Registry(07-4-registry)

Part 5 · 운영 (How-to)
  ├─ 모니터링   (06)
  └─ 성능 튜닝  (10)

Part 6 · 레퍼런스 (Reference, 찾아보기용 — 끝에 모음)
```

### 3.3 핵심 변경 (영향 대비 효과 순)
1. **routing-id(08)를 ROUTER 앞으로** — 가장 명확한 의존성 버그다. ROUTER/STREAM이 이를 전제한다.
2. **Part(그룹) 도입** — 평면 번호를 목적별 7개 Part로 묶어 진입 경로를 만든다.
3. **레퍼런스(02/12)를 뒤로** — core-api가 2번이면 "다 읽어야 하나" 부담이 된다. 끝에 모으고 튜토리얼에서 링크한다.
4. **튜토리얼 신설** — overview §7을 독립 문서로 승격하고 end-to-end로 확장한다.

### 3.4 단계별 실행 (회귀/미러 비용 분리)
`doc/site/docs/guide/`는 verbatim 미러이고 `DocumentationRegressionTests`에 문서
목록·번호 하드코딩 제약이 있다. 그래서 **파괴적 변경(번호 재배치)을 뒤로 미룬다.**

- **A-1 (비파괴, 먼저)**: 파일명·번호를 그대로 두고
  - `doc/guide/README.md`를 신설해 위 Part 구조로 묶은 진입/목차를 작성한다.
  - routing-id ↔ ROUTER/STREAM 교차 링크를 강화한다.
  - 파일 추가만이라 회귀 테스트·미러 영향이 없다.
- **A-2 (튜토리얼)**: `doc/guide/00-getting-started.*`를 신설한다(또는 overview에서 분리).
- **A-3 (파괴적, 마지막)**: 실제 번호를 재배치한다(08→Part2 이동 등).
  - 9.10의 weight 간격 번호 전략으로 파괴성을 완화한다.
  - `DocumentationRegressionTests`의 하드코딩 목록을 동시에 갱신한다.
  - `doc/site/docs/guide/` 미러를 동시에 갱신한다(`cp`).
  - ko/en 쌍을 동시에 이동한다.

## 4. Part B — 언어별 바인딩 가이드

### 4.1 위치와 성격 — 언어당 디렉토리 + 자체 목차 + 주제별 문서
- 위치: **`doc/guide/bindings/<lang>/`** 디렉토리(단일 파일이 아니다). 각 문서는
  `.md`/`.ko.md` 쌍이다.
- 성격: how-to + 튜토리얼. 개념 재설명은 금지하고, 매핑과 언어 고유 규칙만 소유한다.
- granularity 결정:
  - "주제마다 1파일"(16주제 × 7언어 × 2언어 ≈ 224파일)은 **유지보수 폭발 → 기각**.
  - "한 장에 전부"(현재 685줄 dotnet)는 **비좁음 → 기각**.
  - **채택 = 그룹 단위(언어당 index + 5문서)**. gRPC(quickstart/basics/api)·
    RabbitMQ(주제별 페이지) 등 도메인 표준 깊이(언어당 3~6문서)와 일치한다.
- 기준 초안: 현재 `doc/guide/bindings/dotnet.ko.md`(685줄 단일 파일)를 아래 6문서로
  **쪼개 재배치**한다(콘텐츠는 대부분 그대로 + index 신설). 이것이 표준 템플릿이 된다.

### 4.2 고정 문서 세트 (모든 언어 동일) — 코어 가이드 Part를 얇게 미러링

코어 가이드 Part 경계에 1:1 대응시켜 *언어 간*·*레이어 간* 일관성을 함께 얻는다.

| 파일 | 내용 | 대응 코어 Part | 소유/위임 |
|------|------|---------------|-----------|
| `index` | 기능 지도 표(기능→언어타입→한줄→코어링크) + persona 경로 | (진입) | 소유 |
| `01-getting-started` | 설치 + 5분 quickstart(9.1 공유 시나리오) + 핵심 타입(Context/Message/Received/RoutingId) + 소유권 | Part 0 | 소유 ★ |
| `02-messaging` | 소켓 패턴별(PAIR/DEALER·ROUTER/PUB·SUB/XPUB·XSUB/STREAM/Proxy) | Part 2 | 소유 |
| `03-services` | Registry/Discovery/SpotNode·Spot/Actor — 사용법만, 개념은 링크 | Part 4 | 소유(얇게) |
| `04-operations` | 소켓옵션/TLS/모니터링/폴러·타이머/스레딩/네이티브 라이브러리 | Part 3+5 | 소유 |
| `05-reference` | 에러 처리 + 직렬화(코덱) + **C API↔언어 대응표** + 생성 API레퍼런스·샘플 링크 | Part 6 | 소유+위임 |

- 각 문서 머리에 "개념의 정식 정의는 코어가 소유"를 명시하고, 필요한 곳마다 코어
  챕터로 링크한다(황금률, 2장).
- `index`는 5.1 pull 네비게이션의 언어별 진입점이며, persona 경로를 제시한다.

### 4.3 언어 간 일관성 규칙 (gRPC quickstart / RabbitMQ Tutorials 방식)
- **문서 세트·순서·제목 고정** — 위 6문서를 7개 언어 모두 동일 파일명으로 둔다.
- **예제 시나리오 고정** — 9.1 공유 시나리오 매트릭스를 전 언어 공통으로 쓴다. 코드만 관용구 차이.
- **개념 재설명 금지** — "DEALER란?"은 항상 코어 가이드로 링크한다.
- 결과: 한 언어를 익힌 사용자가 다른 언어 가이드를 즉시 읽는다("여기선 Dispose가 close()구나").

### 4.4 롤아웃 순서 (바인딩 성숙도 기준)
1. **dotnet 분할 확정** → 685줄 단일 파일을 6문서로 쪼개 골격을 동결한다(템플릿화). `05-reference`에 C API↔.NET 대응표를 추가한다.
2. **cpp → java → node** (1차 개발 바인딩 — 가이드 동반).
3. **python → go → rust** (후속 바인딩).

### 4.5 언어 중립 템플릿
- `doc/guide/bindings/_template/`를 신설한다 — 6문서 골격을 빈 칸으로 두고, 각 문서·섹션에
  "여기에 무엇을 쓰고 무엇을 링크할지"를 주석으로 단다. 새 언어는 이 디렉토리를 복사해 채운다.

## 5. 통합 진입/네비게이션

- `doc/guide/README.md` (Part A-1) — 코어 가이드 Part 구조 목차 + persona 진입(9.7).
- `doc/guide/bindings/README.md` — "언어 고르기" 진입 표(각 언어의 `index`로 링크):

  | 언어 | 사용 가이드 | 생성 API 레퍼런스 | 패키지 |
  |------|------------|------------------|--------|
  | .NET | `bindings/dotnet/` | docfx | `Systems.Zlink` |
  | … | … | … | … |

- 최상위 `doc/README.md`에 위 두 인덱스로 가는 링크를 추가한다.

### 5.1 읽기 순서(네비게이션) 모델 — 언어 가이드 주도, 코어는 pull-참고

"코어를 먼저 다 읽고 언어 가이드"(push)와 "언어 가이드부터 읽고 필요할 때 코어
참고"(pull)는 별개의 결정이다. **콘텐츠 소유**(개념은 코어에 1번만, 2장)는 그대로
두고, **읽기 순서**는 다음으로 고정한다.

- **기본 = 언어 가이드 주도(pull)**: 사용자는 자기 언어 가이드로 진입하고, 개념이
  필요할 때만 코어로 당겨 본다. RabbitMQ Tutorials·gRPC quickstart가 모두 이 방식
  이며, 실제 사용자(예: .NET 개발자)는 "zlink .NET"으로 들어와 .NET 가이드부터 읽는다.
- **충돌 없음**: "개념 재설명 금지"(4.3)와 양립한다. 언어 가이드 각 섹션은
  **[한 줄 방향 제시] + [코어 개념 링크] + [그 언어 관용 코드]** 형태다. 이는
  재설명이 아니라 방향 제시와 링크이므로, 언어-우선 읽기가 끊기지 않으면서도
  개념 소유는 코어에 남는다.
- **언어 가이드는 단독 진입점으로 완결**되어야 한다(코어 선행 독서 불필요). 이것이
  pull 모델의 전제 조건이다.

진입 인덱스(`doc/guide/README.md`)는 persona별 2경로를 제시한다(9.7과 연결).

```
이미 메시징 아는/빨리 쓰려는 사람  →  [언어 가이드] 바로 → 막히면 코어 링크   ← 기본(pull)
처음 배우는/개념부터 보려는 사람    →  [코어 Part 0~2] → [언어 가이드]          ← 학습 경로(push)
```

코어 가이드는 두 역할을 동시에 갖는다: (a) 학습자용 개념 학습 경로,
(b) 언어 가이드가 링크로 끌어다 쓰는 참고 레퍼런스.

## 9. 도메인 벤치마크 반영 (서버간 통신 라이브러리 기준)

zlink는 서버간 통신 라이브러리이므로, 일반 문서 사례(K8s/Stripe)보다 같은
도메인(RabbitMQ, NATS, Kafka, gRPC, ZeroMQ)의 관행을 우선 반영한다. 아래는 그
벤치마크에서 도출한 추가 개선 항목이다.

### 9.1 공유 시나리오 매트릭스 (RabbitMQ Tutorials 모델) ★
RabbitMQ는 7개 번호 튜토리얼(Hello → Work Queues → Pub/Sub → Routing → Topics →
RPC → Confirms)을 **12개 언어에 동일 시나리오·동일 다이어그램**으로 제공하고,
개념은 한 번만 쓰며 코드만 언어별로 바꾼다.

- zlink도 **정규 시나리오 세트를 한 번 정의**하고(`doc/guide/scenarios.*`), 코어
  가이드(C)와 7개 언어 가이드가 **모두 같은 시나리오를 재사용**한다.
- 1차 정규 시나리오(zlink 소켓/서비스에 맞춤):
  1. **PING/ACK** (PAIR) — 첫 메시지
  2. **부하 분산 작업 큐** (DEALER/ROUTER) — fan-out 워커
  3. **Pub/Sub** (PUB/SUB) — 토픽 fan-out
  4. **요청/응답 RPC** (DEALER↔ROUTER, correlation/timeout)
  5. **Discovery + SPOT** (서비스 계층) — 동적 노드 라우팅
- 효과: 4.3의 "전 언어 동일 시나리오"가 산발 예제가 아니라 **단일 출처 매트릭스**가
  된다. 한 언어를 익힌 사용자가 다른 언어로 즉시 이동한다.

### 9.2 신뢰성·전달 보장 의미 문서 (Kafka delivery semantics / zguide 신뢰성 장) ★
comms 라이브러리 사용자의 1순위 질문은 "이거 메시지 보장이 어떻게 되나"다. Kafka는
delivery semantics(at-most/at-least/exactly-once)를, zguide는 "Reliable
Request-Reply" 장을 따로 둔다. 지금 우리 가이드는 이 내용이 여러 곳에 흩어져 있다.

- Part 1(개념)에 **전달 보장·신뢰성** 전용 문서를 신설하고 다음을 명시한다:
  - 순서 보장 범위, HWM/backpressure 시 동작(블록 vs drop vs false 반환)
  - 연결 끊김·재연결 시 in-flight 메시지의 운명
  - request timeout 의미, 중복·유실 가능성, 멱등성 책임 경계
  - 각 소켓 패턴별 보장 차이표

### 9.3 설계 근거(왜) 문서 (Kafka Design 섹션)
Kafka Design 섹션은 zero-copy, page cache, 복제 같은 **엔지니어링 근거**를
사용자용으로 설명해 평가·신뢰를 얻는다. zlink는 이미 zero-copy/VSM, lock-free
YPipe, Proactor, 8개 소켓 타입 축소 같은 강한 설계 서사를 갖췄다.

- Part 1(개념)에 **"왜 이렇게 설계했나"** 문서를 두고, 깊은 내용은
  `doc/internals/`로 링크한다(internals는 메인테이너용으로 유지하되, 사용자용
  요약 진입은 가이드에 둔다).

### 9.4 wire protocol(ZMP) 레퍼런스 (NATS/zguide protocol spec)
NATS·ZeroMQ는 wire protocol 명세를 공개해 interop과 **새 바인딩 작성**을
가능케 한다. zlink는 ZMP v1.0(8B 고정 헤더)이 있으나 사용자 가이드에 드러나지 않는다.

- Part 6(레퍼런스)에 **ZMP 프로토콜 레퍼런스**를 추가한다(또는 internals에서 승격).
  대상: 새 언어 바인딩 작성자, 타 시스템 interop.

### 9.5 예제 = 컴파일되는 샘플에서 추출 (writethedocs / RabbitMQ)
유명 가이드는 예제를 **CI로 컴파일·실행되는 샘플에서 추출**해 드리프트를 막는다.
`bindings/<lang>/samples/`가 이미 있으므로 이를 단일 출처로 삼는다.

- 가이드 코드 블록은 손으로 쓰지 않고 샘플 파일의 **명명된 스니펫 영역**에서
  추출한다(또는 최소한 샘플과 1:1 대응 + 스모크 테스트로 검증한다).
- 효과: 코드 예제가 깨지면 빌드가 깨진다 → 문서 코드 부패를 막는다.

### 9.6 용어집(Glossary) (K8s)
zlink는 SPOT, Actor, routing-id, 역할, channel, ZMP, VSM, HWM 등 용어가
많다. framework 가이드는 각주로 처리 중이나, 코어에는 중앙 용어집이 없다.

- `doc/guide/glossary.*`를 신설한다. framework 가이드의 각주 정의와 정합을 맞추고,
  각 가이드 문서가 용어집으로 링크하게 한다.

### 9.7 persona 진입점 (K8s 홈페이지)
Part 구조는 목적 기반이지만, 진입 인덱스에 **역할별 입구**를 추가한다.

- 앱 개발자 → Part 0~2 / 운영자 → Part 5 / 바인딩 작성자 → spec + 9.4 protocol +
  9.5 샘플 / 평가자 → 9.3 설계 근거 + 9.2 신뢰성.

### 9.8 버전/호환성·마이그레이션 (Kafka Upgrading / K8s 버전 스위처)
core 6.0.x로 버전이 오르고 바인딩 정렬이 진행 중인데, 문서에 버전 전략이 없다.

- **core↔binding 버전 매트릭스**(어느 바인딩이 어느 core 계약에 정렬됐는지),
  버전 간 호환성·마이그레이션 노트 문서를 신설한다.
- (선택) "libzmq/ZeroMQ에서 넘어오기" 포팅 문서 — zlink가 libzmq 기반이라 적은
  비용으로 도입 마찰을 낮춘다.

### 9.9 문서 스타일·다이어그램 가이드 (K8s contribute/style)
다수 기여자·다국어에서 일관성을 유지하려면 스타일 규약이 필요하다.

- **문서 스타일 가이드** 신설: 챕터 템플릿(3.1의 Redis식 `개요→사용→옵션→패턴→주의`),
  네이밍, 링크 규칙.
- **다이어그램 규약** 명문화: 적층 레이어는 ASCII, 흐름/시퀀스는 Mermaid
  (기존 정책 그대로 문서화).

### 9.10 weight 간격 번호로 P8 파괴성 완화 (K8s weight 10/20/30)
K8s는 순차 번호(1,2,3) 대신 **간격 번호(10,20,30)**로 페이지를 정렬해, 중간 삽입
시 전체 재번호를 피한다.

- 코어 가이드 재배치(P8) 때 파일 순서를 간격 번호나 front-matter `weight`로
  표현하면, 이후 문서 삽입이 비파괴가 된다.
- `DocumentationRegressionTests`의 하드코딩 목록도 "순서 번호" 대신 "존재/그룹"
  검증으로 바꾸면 향후 변경 비용이 더 준다.
