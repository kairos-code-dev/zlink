# ZLink HTTP Client — 성능 측정과 비교 (perf)

> 이 문서는 5개 언어 HTTP client의 성능 측정 시나리오·지표·비교 규칙의
> 정본이다. 측정 결과 기록표는 이 디렉터리에 언어별 파일로 누적한다
> (`<lang>-results.ko.md`, 최초 측정 시 생성).

## 1. 목적

- 언어 간 상대 성능(같은 서버, 같은 시나리오)을 주기적으로 비교해 특정
  언어 래퍼의 오버헤드 회귀를 감지한다.
- 래퍼 오버헤드를 **네이티브 스택 직접 사용 대비**로 측정한다. 목표는
  "래퍼 비용이 네이티브 대비 상수 수준"임을 유지하는 것 —
  격차 해소는 래퍼 오버헤드 축소로 하고, 스레드/풀 상수 조작으로 하지 않는다.

## 2. 측정 규칙 (framework perf 공통 규칙 준수)

- **성능 관련 변경은 baseline vs patched 비교 측정 없이 커밋하지 않는다.**
- 서버는 측정 대상이 아니므로 고정한다: 같은 머신의 in-process/localhost
  echo 서버(각 언어 하네스가 동일 응답 스펙을 구현), keep-alive 활성.
- 워밍업 후 측정, 3회 반복 중앙값. 동시 실측 경합을 피하기 위해 언어별
  하네스를 순차 실행한다.
- 장시간 실행은 3분 간격 하트비트로 모니터링한다.

## 3. 시나리오 매트릭스

| ID | 시나리오 | 측정 의도 |
| --- | --- | --- |
| H1 | GET 소형(256B) 응답, keep-alive 재사용, 순차 | 요청당 래퍼 고정 비용(빌더/헤더/에러 봉투) |
| H2 | H1을 동시성 1/8/64로 | 실행 모델 확장성(직렬화·락 병목: cookie jar, cpp 스케줄러) |
| H3 | POST typed JSON 1KiB 왕복 (`body(dto)`→`submit<T>`) | 직렬화/디코드 경로 + raw_body 이중 보유 비용 |
| H4 | GET 대형(16MiB) 버퍼링 응답 | body 복사 횟수(전량 버퍼링 경로) |
| H5 | `download(sink)` 대형(64MiB) | 스트리밍 경로, chunk 복사 |
| H6 | `bodyStream` 업로드(64MiB) | chunked 업로드 경로 |
| H7 | H4 + gzip `compression()` | 압축 해제 비용(node 동기 zlib 블록 검증 포함) |
| H8 | 신규 client 생성+단일 요청+close 반복 | one-shot 경로 비용(핸들러/연결 생성) — R7 판단 근거 |

## 4. 지표

- 처리량: req/s (H1~H3), MiB/s (H4~H7)
- latency: p50 / p99 (H1~H3, 동시성별)
- 자원: 피크 RSS, (가능 언어) 할당량/GC 횟수, event loop 지연(node, H7)
- 비교 축: ① 언어 간 상대비 ② 네이티브 스택 직접 사용 대비 오버헤드 %
  ③ 이전 기록 대비 회귀 %

## 5. 하네스 위치

- `harness/node-h7-compression.js` — H7(node, gzip 해제 경로). 기록:
  [node-results.ko.md](node-results.ko.md).
- 나머지 시나리오(H1~H6, H8, 타 언어)는 하네스 미작성 — 추가되는 대로
  `harness/<lang>-h<N>-*.{js,cs,java,cpp}` 규약으로 두고 이 절에 등재한다.

## 6. 회귀 판정

- 동일 시나리오에서 이전 기록 대비 처리량 −5% 또는 p99 +10%를 넘으면 회귀로
  간주하고 원인 규명 전 커밋 금지.
- 언어 간 비교는 절대치가 아니라 **네이티브 대비 오버헤드 %**로 판정한다
  (전송 스택 자체 성능 차이는 래퍼 책임이 아님).
