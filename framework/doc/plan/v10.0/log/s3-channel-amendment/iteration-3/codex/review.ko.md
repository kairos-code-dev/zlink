## Findings

[계약][high] framework/doc/framework/spec/90-implementation-gap.ko.md:419 — Java runtime options gap이 `channel(meshName, channelName)`과 서로 다른 MeshName의 같은 ChannelName을 독립 설정하는 테스트를 목표로 남겨 두어 현재 목표 계약과 정반대다 — Java 정확 인터페이스는 `channel(String channelName)`만 선언하고(`server/languages/java/02-handler-interfaces.ko.md:1707`), 공통 계약은 process-local ChannelName이 물리 topology 하나만 선택하며 중복 등록을 startup 오류로 규정한다(`server/10-channel-topology.ko.md:41`, `server/10-channel-topology.ko.md:45`) — §12.26을 ChannelName 단독 runtime option과 process-local 충돌 계약으로 고치고, 구형 2인자 signature와 동일 process의 중복 ChannelName 허용 문구를 verifier의 금지 조건으로 추가한다.

[계약][high] framework/doc/framework/spec/server/languages/node/02-handler-interfaces.ko.md:578 — 목표 정확 인터페이스에 generic peer 모델의 `Fanout` auto-connect type과 `Pub`·`Sub` role이 남아 fanout 전용 descriptor 계약과 두 개의 공개 모델을 만든다 — 같은 언어의 location-store 목표 계약은 fanout이 generic `ZLinkPeerLocation`의 row·stamp·조회 API를 재사용하지 않는다고 규정하고(`server/languages/node/04-location-store.ko.md:316`), 공통 계약도 전용 kind·key·query를 요구한다(`server/40-location-runtime.ko.md:72`). 그런데 generic peer filter/key/resolver가 auto-connect type과 role을 계속 공개한다(`server/languages/node/02-handler-interfaces.ko.md:995`) — generic peer 표면에서 Fanout 및 Pub/Sub 값을 제거해 RouteMesh 전용 의미로 한정하고, 모든 언어의 정확 인터페이스와 inventory에서 fanout 조회는 전용 publisher descriptor/store만 사용하도록 고정한다.

[계약][blocker] framework/doc/framework/spec/server/languages/java/02-handler-interfaces.ko.md:918 — 다섯 언어의 classic fanout 발행 public contract가 없거나 topic 기반·무결과 호출로 서로 달라 Config 3의 packet-name typed publish를 공통 public API로 구현할 수 없다 — 공통 계약은 framework가 typed payload에서 packet name을 결정하고 classic fanout caller는 fanout ChannelName만 제공하며 transport topic filter를 노출하지 않는다고 규정하고(`05-framework-api.ko.md:103`, `05-framework-api.ko.md:112`, `05-framework-api.ko.md:256`), 모든 send/publish가 bounded admission 결과를 반환해야 한다(`04-async-execution-policy.ko.md:37`). 그러나 Java는 `publish(channelName, topic, message)` 뒤 `void submit()`을 선언하고, Kotlin은 `publishToTopic`, Node는 topic과 Logical Multicast detail의 `ZLinkPublishCall`, C++는 topic을 받는 `void publisher_t::publish`를 선언하며, .NET 정확 인터페이스에는 classic fanout outbound client 자체가 없다 — classic fanout client·call·admission result의 정확 signature를 다섯 언어에 먼저 정의하고 packet name은 typed registration/metadata 규칙으로 결정하며 topic을 제거한다. Logical Multicast result와 분리하고 compile fixture·inventory·Config 3에서 동일 public 동작을 검증한다.

[계약][high] framework/doc/framework/common/e2e/config-3-pubsub.ko.md:151 — automatic subscriber의 제외 규칙 가운데 draining publisher와 같은 RID의 낮은 lifecycle generation·descriptor revision을 실제 connection set에서 배제하는 시나리오가 없다 — 정식 location 계약은 다른 kind·ChannelName뿐 아니라 draining, expired, lower generation/revision을 모두 제외한다(`server/40-location-runtime.ko.md:224`). PS-D2는 다른 ChannelName과 descriptor kind만 넣고, PS-D4는 lease 만료 뒤 새 generation만 확인해 최신 snapshot 뒤 늦게 나타난 낮은 generation/revision record를 검증하지 않는다. 다섯 feature map도 같은 축을 그대로 누락한다 — PS-D2/PS-D4 또는 별도 P0 시나리오에 draining revision과 최신 snapshot 이후 주입한 낮은 generation/revision row를 추가하고 연결 없음·기존 연결 제거·복구 수렴을 판정한다. Automatic/manual mode 혼합과 fixed/allocated RID 중복 설정의 startup 회귀도 Config 3 및 다섯 feature map에 전용 행으로 추가한다.

[원칙][high] framework/doc/framework/spec/server/languages/java/01-system-structure.ko.md:97 — location store를 등록한 automatic fanout 예제가 publisher RID를 선택하지 않아 문서의 목표 API 그대로 실행하면 startup 계약을 위반한다 — store 등록 publisher는 startup 전에 fixed 또는 allocated Publisher RID를 반드시 선택해야 한다(`server/40-location-runtime.ko.md:94`, `server/languages/java/02-handler-interfaces.ko.md:645`). C++의 automatic subscriber 예제도 RID와 location store 없이 `enable_publisher(...).enable_subscriber()`를 제시한다(`server/languages/cpp/02-framework-interfaces.ko.md:1931`) — 두 예제에 fixed/allocated Publisher RID와 공식 store 등록을 함께 보이거나, store 없는 완전한 manual publisher/subscriber 예제로 바꾸어 복사 가능한 예제가 startup validation을 통과하게 한다.

[계약][high] framework/doc/framework/spec/server/languages/cpp/02-framework-interfaces.ko.md:1858 — C++ 정확 계약이 모든 MeshNode에 하나 이상의 ChannelName을 요구해 membership 0개 MeshNode를 금지한다 — Core 정식 계약은 ChannelName 0개를 허용하고(`core/doc/spec/core/service/01-mesh-node.ko.md:13`, `core/doc/spec/core/service/01-mesh-node.ko.md:161`), framework 공통 계약과 Config 12도 호출·direct 전용 MeshNode 및 `WorkflowServer`의 membership 0개를 명시한다(`server/10-channel-topology.ko.md:33`, `common/e2e/config-12-channel-egress-routing.ko.md:41`) — C++ 문구를 handler를 제공하는 MeshNode만 Server membership이 필요하다는 공통 startup 규칙으로 고치고 membership 0개 compile/config fixture를 추가한다.

[계약][medium] framework/doc/framework/spec/server/languages/cpp/02-framework-interfaces.ko.md:1854 — 같은 packet name의 handler 중복을 request protocol 오류로 분류해 startup configuration 오류와 runtime protocol 오류를 섞는다 — handler key 중복은 host가 메시지를 받기 전에 검증하는 startup 오류이고(`05-framework-api.ko.md:353`, `05-framework-api.ko.md:363`), `request_protocol_error`는 request completion/error envelope의 protocol 의미다(`server/languages/cpp/02-framework-interfaces.ko.md:119`) — 중복 등록은 C++의 명시적인 options/startup configuration error로 고정하고 `request_protocol_error`는 malformed runtime request·reply에만 사용하도록 compile-negative 및 startup test를 추가한다.

[원칙][high] scripts/verify-framework-doc-contracts.sh:951 — verifier가 성공하지만 위 classic fanout publish·generic peer·drain/stale·구형 Java runtime option 모순을 의미적으로 검증하지 않아 잘못된 exact contract hash를 정상 계약으로 고정한다 — 현재 semantic 검사는 PubSub PS-A2 행의 단어, PS-D2의 subscriber descriptor 부재, Logical Multicast의 MeshName 부재만 확인하고, inventory required fragment도 fanout builder와 store만 요구해 fanout outbound client/signature와 금지 표면을 확인하지 않는다(`framework/doc/contract-inventory/route-mesh-v10-contract-inventory.json:47`) — 다섯 언어별 classic fanout client의 ChannelName+typed payload+admission-result declaration을 구조적으로 추출해 검증하고 topic·generic Fanout role·2인자 runtime channel을 금지하며, Config 3의 drain/stale 시나리오와 다섯 feature-map 전용 행을 semantic gate로 추가한다.
