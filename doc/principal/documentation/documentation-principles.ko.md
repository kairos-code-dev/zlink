# zlink 문서화 원칙

> AI 에이전트가 zlink 문서를 생성·검토·통합할 때 바로 적용할 수 있는 행동 규칙으로
> 정리한 문서. core·bindings 문서를 **개념은 한 번만, 코드는 언어 탭으로** 통합하는
> 방향(원칙 1~7), **한글 산문을 서버 개발자가 바로 읽히게 쓰는 문체 규칙**(원칙 8,
> 모든 문서 공통), **framework 문서를 언어별로 완결하게 두는 반대 전략**(원칙 9),
> **문서는 현재 상태만 담는다는 규칙**(원칙 10), 그리고 **작성 후 Codex 2축 리뷰로
> 검증하는 절차**(원칙 11)를 정의한다.

---

## 핵심 전제

**zlink는 C 코어 + 8개 언어 바인딩(C, C++, Java, Python, Node/TS, C#/.NET, Go, Rust)을
가진 다국어 메시징 라이브러리다.** 문서화의 근본 문제는 **중복**이다.

같은 개념(예: Actor의 재접속 이전성)을 8개 언어로 복제하면 하나를 고칠 때 8곳을
고쳐야 하고(변경 증폭), 곧 서로 어긋난다(drift). 반대로 개념을 C 코드로만
설명하면 다른 언어 사용자가 자기 코드를 못 찾아 읽기를 포기한다(인지 부하).

모든 문서화 결정은 다음을 기준으로 평가한다:

| 기준 | 질문 |
|------|------|
| **중복 최소** | 같은 개념이 여러 곳에 복제되지 않는가 |
| **언어 접근성** | 각 언어 사용자가 자기 언어 코드를 바로 찾는가 |
| **검증 가능** | 문서의 코드가 실제 API와 맞는지 기계가 확인하는가 |
| **drift 저항** | 시간이 지나도 코드와 문서가 어긋나지 않는가 |

이 "중복 최소" 기준은 **core·bindings 문서**에 적용된다. 상위 계층인 **framework
문서는 단일 언어 독자의 완결성을 위해 언어 간 중복을 의도적으로 허용하는 반대 전략**을
쓴다(원칙 9).

코드 안에 작성하는 공개 API 주석과 내부 주석은 별도 원칙을 따른다:

**[`source-comment-principles.ko.md`](../source-comment-principles.ko.md)**

문서 파일은 독자와 목적에 맞춰 guide/spec/internals로 나누고, 소스 주석은
호출자가 API를 올바르게 쓰는 데 필요한 계약을 짧게 설명한다. 사용법과 예제는
소스 주석이 아니라 guide 문서에 둔다.

## 원칙 1 — 개념은 한 번만, 코드는 언어 탭으로

**한 문서가 개념을 한 번 설명하고 코드 예제는 언어별 탭으로 나란히 둔다.**

이것이 zlink 문서화의 중심 형태다. zguide(zeromq.org) 패턴을 따르며 mkdocs
Material의 `pymdownx.tabbed`로 렌더한다.

```markdown
Actor는 세션과 별개로 존재해 재접속해도 같은 엔티티로 이어진다. (개념 — 언어 무관)

=== "C"
    ```c
    zlink_spot_node_actor_new(node, "player-42", &ref);
    ```
=== "C#"
    ```csharp
    var actor = node.CreateActor("player-42");
    ```
=== "Rust"
    ```rust
    let actor = node.create_actor("player-42")?;
    ```
```

**왜:**
- 개념은 한 곳에만 있어 중복이 0이다.
- .NET 사용자는 C# 탭만 보면 되고 C 포인터 코드에 막히지 않는다.
- 코드가 같은 문서에 모여 있어 한 곳을 열면 여러 언어를 비교할 수 있다.

**트레이드오프(수용함):** 마크다운 소스(`.md` raw)는 `=== "C#"` 마크업으로
덜 읽힌다. 탭 UI는 **빌드해야** 보인다(아래 원칙 5). 이 비용을 받아들인다.

### 탭 언어 분류

| 분류 | 언어 | 비고 |
|------|------|------|
| 네이티브 바인딩 | C, C++, C#/.NET, Java, Node/TypeScript, Python, Go, Rust | 8개 |
| 런타임 공유 | Kotlin(JVM), JavaScript(Node) | 2개, 별도 탭 칸 |
| 합계 | | 전체 표면 10개 언어 |

탭 칸 수는 **문서마다 다르다.** "그 문서에 해당하는 샘플이 존재하는 언어"만 탭에
넣고 없는 언어 탭을 비워 두지 않는다.
- 소켓 패턴 문서(pair/dealer 등)는 C 샘플이 있어 **C 포함 최대 10칸**.
- 서비스 문서(actor 등)는 해당 C 샘플이 없으면 **C 제외 9칸**.
- JVM은 `Java`/`Kotlin` 두 칸, Node는 `Node/TypeScript`/`JavaScript` 두 칸으로
  나눈다(같은 런타임이라도 언어가 다르면 별도 탭).

## 원칙 2 — 디렉토리는 성격대로, 탭 적용도 성격대로

`doc/` 아래 디렉토리는 독자와 목적이 다르며 **탭 적용 여부도 그 성격을 따른다.**

| 디렉토리 | 독자 | 탭 적용 |
|----------|------|---------|
| `doc/guide/` | 라이브러리 사용자 | **언어 탭** (코어 가이드의 코드 예제) |
| `doc/internals/` | core 유지보수자 | **2분류** (아래) |
| `doc/spec/` | 바인딩 개발자 | **언어별 분리 유지** (탭 아님) |

### internals의 2분류

internals 안에서도 두 성격이 갈리며 탭 적용을 달리한다.

| 성격 | 예 | 적용 |
|------|-----|------|
| **순수 코어 내부** | reaper, io_thread 스케줄링, YPipe CAS, 소켓 배선 | **C-only** — 바인딩과 무관, 언어 탭 무의미 |
| **바인딩이 표면화하는 내부** | 소유권/zero-copy, 스레드 모델, 콜백 dispatch, VSM 비용 | **언어 비교 탭** — "이 내부 동작이 내 언어에선 어떻게 보이나" |

바인딩이 표면화하는 internals는 단순 C 덤프가 아니라 **"C 코어 동작 + 각 언어가
그 비용·소유권을 어떻게 노출하나"의 비교**가 된다. 예: zero-copy를 C는
`zlink_msg_init_data`로, C#은 `AsSpan()` 네이티브 버퍼 뷰로, Rust는 `&[u8]`
빌림으로, Java는 `MemorySegment`(FFM)로 표면화한다 — 이 비교가 사용자에게 가치다.

### spec은 탭으로 합치지 않는다

spec은 **언어별 공개 계약**이라 이미 `spec/bindings/<lang>`으로 분리돼 있다.
계약은 언어마다 시그니처·반환·오류가 다르므로 한 문서에 탭으로 합치기보다 현
분리 구조가 맞다. spec의 단일 기준은 `core/include/zlink.h`다.

## 디렉토리별 작성 원칙

각 디렉토리는 [AGENTS.md](../../../AGENTS.md)가 정의한 독자·목적을 따른다. 아래는
그 위에 얹는 **구체 작성 규칙**이다. 한 문장으로: **guide는 "어떻게 쓰나",
internals는 "어떻게 동작하나", spec은 "무엇을 보장하나"에만 답한다.**

### guide 작성 원칙 (사용자)

**목적:** 사용자가 "이걸 어떻게 쓰지?"라고 물을 때 답이 된다.

- **구조:** `개요(한 줄 정의 + 언제 쓰나) → 기본 사용법 → 옵션 → 사용 패턴 →
  주의사항/더 보기`. 서비스·상위 기능은 `역할(무엇) → 언제(결정 기준) → 사용
  형태`. "기능 나열"이 아니라 **"언제·왜"**가 들어가야 가이드다.
- **코드는 언어 탭으로**(원칙 1). 개념은 탭 밖에 한 번, 코드는 언어 탭 안에.
- **내부 구현을 넣지 않는다.** 사용자는 내부 소켓·inproc endpoint·YPipe를 알 필요가
  없다. 내부 동작을 참고해야 하면 internals를 **링크**한다.
- **결정 기준을 표로.** "A vs B를 언제" 같은 선택은 산문보다 표가 낫다(예: 소켓 패턴
  선택, AutoConnectType 고르기).
- **실패·경계를 정직하게.** 보장되지 않는 것(PUB slow-joiner, 재연결 시 유실)을
  숨기지 않는다. 사용자가 가장 데이는 지점이다.
- **값은 production-like.** 포트·심볼·금액을 현실적으로. 같은 시나리오는 전 언어가
  같은 값을 공유한다(공유 시나리오 매트릭스).

### internals 작성 원칙 (유지보수자)

**목적:** core 개발자가 코드를 읽기 전에 전체 그림을 잡는다.

- **다이어그램 중심.** 소켓 배선·데이터 흐름은 산문보다 그림으로. 적층은 ASCII,
  흐름·시퀀스는 Mermaid(원칙: 다이어그램 규약).
- **"왜 이렇게 설계했나"를 먼저.** 구조만 나열하지 말고 그 구조가 푸는 문제를 앞에
  둔다(예: spot-internals의 "§0 왜 이렇게 설계되었는가").
- **2분류를 의식한다**(원칙 2): 순수 코어 내부는 C-only, 바인딩이 표면화하는
  내부(소유권·zero-copy·스레드·콜백)는 **언어 비교 탭**으로 "각 언어가 이 내부를
  어떻게 노출하나"를 보인다.
- **사용법을 넣지 않는다.** "어떻게 쓰나"는 guide의 몫이다. internals는 구조만.
- **코드 위치를 가리킨다.** 설명한 동작이 어느 파일·구조체에 있는지 짚어 독자가
  소스로 바로 갈 수 있게 한다.

### spec 작성 원칙 (바인딩 개발자·계약 검토자)

**목적:** 각 바인딩이 **무엇을 보장해야 하는가**를 정의한다(어떻게 보이는가가
아니라).

- **단일 기준은 `core/include/zlink.h`.** 코어 C 계약이 유일한 진실이며 각 언어
  spec은 그 계약을 자기 언어로 어떻게 투영하는지 정의한다.
- **계약만, 사용법 금지.** 공개 타입·메서드·시그니처·반환값·오류 의미·소유권
  규칙만. "언제 쓰나"·튜토리얼은 guide로.
- **계약에 없는 동작은 보장하지 않는다.** spec에 적히지 않은 동작에 의존하지 말라는
  뜻이며 문서도 그 경계를 명확히 한다.
- **언어별 분리 유지**(탭 아님, 원칙 2). 계약은 언어마다 시그니처·반환·오류가 달라
  `spec/bindings/<lang>`로 나뉜다.
- **blueprint다, 코드 추종이 아니다.** spec은 바인딩이 도달해야 할 목표 형태를
  정의한다. 코드가 spec과 다르면 코드를 고치지, spec을 코드에 맞춰 바꾸지 않는다.
- **검증 가능한 계약.** 가능하면 각 계약이 어떤 contract 테스트로 보장되는지 연결해
  "문서에만 있는 계약"이 되지 않게 한다.

## 원칙 3 — 언어 고유 내용은 탭에 욱여넣지 않는다

코드 한 줄로 탭에 들어가지 않는 **언어 고유 내용**이 있다. 이건 코어 탭 문서로
흡수하지 말고 언어별 가이드 **1장**(`doc/guide/bindings/<lang>.md`)에 얇게 남긴다.

| 탭에 안 맞는 것 | 왜 |
|----------------|-----|
| 설치 | `npm install` vs `dotnet add` vs Maven vs cargo — 절차가 언어마다 통째로 다름 |
| 소유권 모델 | `using`/`Dispose` vs `defer`/`Close` vs `Drop` vs try-with-resources |
| 에러 처리 스타일 | 예외 vs `error` 반환 vs `Result` |
| C API ↔ 언어 대응표 | 그 언어만의 매핑 |
| 패키징·배포 | AOT, self-contained, 네이티브 로딩 |

**규칙:** 코드 예제(메시징·서비스 사용법)는 코어 탭 문서로 올리고 위 항목은 언어
가이드 1장에 남긴다. 언어 가이드는 "흡수되어 사라지는" 것이 아니라 **"언어 고유
규칙만 남기고 1장으로 얇아진다."** 메시징 코드는 코어 탭으로 가고
설치·소유권·에러·대응표·배포는 잔류한다.

> **바인딩 가이드 1장 구조** (`doc/guide/bindings/<lang>.md`):
> 설치 → 소유권·정리 모델 → 패키징/배포 → C API↔언어 대응표 → "메시징·서비스
> 사용법은 코어 가이드 탭으로" 안내. 기존 6문서(index/01~05) 중 02~04와 05의
> 코드·샘플 링크는 코어 탭이 흡수하므로 삭제하고 위 언어 고유 항목만 1장으로
> 회수한다.
>
> **런타임 공유 언어**(Kotlin, JavaScript)는 별도 가이드를 두지 않고 그 런타임의
> 네이티브 가이드 1장에 절로 추가한다(Kotlin→java 가이드, JavaScript→node 가이드).
> 설치·소유권이 거의 같고 언어 문법만 다르기 때문이다.

## 원칙 4 — 모든 탭 코드는 실재하는 API여야 한다

**존재하지 않는 메서드를 지어내지 않는다.** 여러 언어 × 다수 문서면 추측 API가
무수히 생긴다. 탭에 쓰는 모든 호출은 해당 바인딩의 `Contracts/`·소스·헤더에
실재해야 한다.

- 의심되면 그 언어의 공개 계약을 직접 확인한 뒤 쓴다.
- 가능하면 `bindings/<lang>/samples/`의 실행되는 샘플과 1:1로 대응시킨다.
- 조사 보고서나 기억에 의존하지 말고 **1차 소스로 검증**한다. (이 원칙이 없으면
  실제로 없는 API가 문서에 박힌다.)

값은 현실적인 production-like 값을 쓰고 같은 시나리오는 전 언어가 같은 값을
공유한다(공유 시나리오 매트릭스).

## 원칙 5 — 규칙은 CI가 강제한다 (문서로만 두지 않는다)

**규칙이 문서로만 있고 강제 장치가 없으면 반드시 어겨진다.** zlink는 이미 한 번
언어 탭 문서 전체가 한 커밋에서 C-only로 덮여 사라진 적이 있다. 같은 일을 막는
것은 "탭을 지우지 말자"는 권고가 아니라 **지우면 빌드가 깨지는 장치**다.

| 규칙 | 강제 방법 |
|------|----------|
| 탭 문서는 언어 탭을 모두 가진다 | 회귀 테스트: `=== "<lang>"` 누락 문서 검출 |
| 탭 코드의 API가 실재한다 | 코드블록 추출 → 컴파일/스모크 (예제=샘플 규약) |
| 탭이 통째로 사라지는 변경 차단 | 탭 마크업 수 급감 시 CI 실패 |
| 원본·미러·ko/en 동기 | 일치 검사 |

탭 마크업 수, 언어 커버리지, 미러 동기화를 측정하는 회귀 테스트를 문서 변경
파이프라인에 둔다. **새 규칙을 만들면 그 규칙을 깨는 변경을 잡는 검사를 함께
만든다.**

## 원칙 6 — 미리보기는 빌드 후, 확인 없이 완료로 보지 않는다

탭 마크업(`=== "C#"`)은 일반 마크다운 텍스트이며 **탭 UI는 mkdocs로 빌드해야
보인다.** GitHub raw나 일반 프리뷰에서는 `=== "C#"` 글자 그대로다.

- 로컬 확인: `cd doc/site && mkdocs serve` → `http://127.0.0.1:8000` 실시간 렌더.
- 정식 배포는 그다음(`gh-deploy` 또는 CI).
- **탭이 의도대로 렌더되는지 빌드로 눈으로 확인하기 전까지 완료로 보지 않는다.**

## 원칙 7 — 큰 통합은 파일럿으로 패턴을 먼저 확정한다

코어 guide + 바인딩이 표면화하는 internals를 언어 탭으로 바꾸는 일은 수십
문서 × 여러 언어 규모다. 한 번에 전부 바꾸면 동시 편집 충돌·추측 API가 대량으로
터진다.

**절차:**
1. 대표 문서 1개를 파일럿으로 골라 개념 + 언어 탭으로 만든다(예: `07-4-actor`).
2. `mkdocs serve`로 실제 탭 렌더를 확인한다.
3. 그 과정에서 탭 마크업 규칙·회귀 테스트·언어 고유 내용 잔류 방식을 한 문서에서
   검증한다.
4. 좋으면 그 패턴을 나머지 문서에 확대하고 아니면 싸게 고친다.

검증된 패턴 없이 전면 변환을 시작하지 않는다.

## 원칙 8 — 한글 산문은 서버 개발자가 바로 읽히게 쓴다

원칙 1~7이 **문서의 구조·형태**(탭·디렉토리·검증)를 다뤘다면, 이 원칙은 **문장
자체의 문체**를 다룬다. 같은 내용이라도 영문을 그대로 옮긴 듯한 문장은 한국어
독자도 다시 영어로 머릿속에서 번역해야 읽힌다. zlink 문서의 산문은 한국어로 쓰되
**한국어 서버 개발자가 한 번에 읽히게** 쓴다.

이 원칙은 [AGENTS.md](../../../AGENTS.md)의 문서 작성 규칙을 구체화한 것이다.
문서 본문에서는 금지 표현을 피하고, 필요하면 쉬운 한국어로 풀어서 다시 쓴다.
짧은 규칙의 단일 기준은 AGENTS.md이고, 아래는 그 실행 지침이다.

### 8.1 독자는 서버 개발자다 — 아는 용어는 영어 그대로

대상 독자는 네트워크·동시성을 다루는 서버 개발자다. 그들이 일상적으로 영어로
쓰는 전문 용어는 **굳이 한국어로 옮기지 않는다.** 표준 용어를 어색한 한국어로
바꾸면 오히려 더 안 읽힌다.

| 그대로 둘 용어(예시) |
|----------------------|
| socket, queue, thread, callback, dispatch, facade, payload, buffer, pipe, endpoint |
| data plane, control plane, peer, router, routed, mesh, fanout, session |
| HWM, backpressure, throughput, latency, poller, signaler, snapshot, profile, override |

**두 가지를 모두 금지한다:**

| 금지 | 나쁜 예 | 대신 |
|------|---------|------|
| 한자 번역 | dispatch→“분배”, data plane→“데이터 평면”, transport→“전송” | `dispatch`, `data plane`, `transport` 그대로 |
| 한글 음차 | facade→“파사드”, dispatch→“디스패치” | `facade`, `dispatch` 그대로 |

> 음차(파사드/디스패치)가 특히 나쁘다 — 영어도 한국어도 아니라서 독자가 원래 영어
> 단어로 되돌려 읽어야 한다. 영어 그대로가 가장 빨리 읽힌다.

`mesh`는 영어로 둔다. “메시”로 음차하면 “메시지(message)”와 헷갈린다.

단, `소켓`·`콜백`·`버퍼`·`메모리`처럼 **한국어에 이미 완전히 굳은 외래어**는 음차해도
된다. 이 규칙이 겨냥하는 건 아직 덜 정착한 용어(`디스패치`·`파사드`·`드리프트` 등)다 —
이런 건 음차하지 말고 영어 단어 그대로 둔다.

### 8.2 용어는 “그림 먼저, 이름은 꼬리표”로 들인다

8.1이 “아는 용어는 그대로”라면, 처음 보는 개념어·추상어는 **그 용어를 안다고 전제하지
말고**, 그게 *무슨 일을 하는지*를 먼저 그려 준 뒤 이름을 그 그림에 붙인다. "용어 →
뜻풀이" 순서가 아니라 **"그림 → 이름(꼬리표)"** 순서다. 이러면 독자 머릿속에 그림이
먼저 서고, 용어는 외워야 할 전제가 아니라 그 그림의 라벨이 된다.

- **그림을 먼저.** 추상명사(평면·계층·패턴)로 시작하지 말고, 그게 물리적으로 하는 일을
  동작 동사로 그린다(8.4와 같은 결).
- **이름은 꼬리표로.** 그림이 선 다음 "이걸 X라 부른다"로 붙인다.
- **코드에 박힌 이름은 지우지 말 것.** `data plane`(= `spot_data_plane_loop_t`),
  `facade`(= `spot_handle_t`)처럼 소스 심볼·디렉토리에 쓰이는 이름은 산문에서 빼면 코드와
  연결이 끊긴다(8.5). 지우지 말고, **그림을 먼저 그린 뒤 코드 대조용 꼬리표**로 남긴다.

| 용어 | Before (이름을 안다고 전제) | After (그림 먼저 → 이름 꼬리표) |
|---|---|---|
| data plane | "data plane 스레드는 `SpotNode`당 하나씩 두는 전용 OS 스레드다." | "**한 노드의 실제 메시지가 전부 지나가는 ‘외길’ 스레드**다 … 소스에선 이 스레드를 `data plane`이라 부른다." |
| facade | "`Spot`은 빌려 쓰는 facade다." | "`Spot`은 실체를 직접 안 들고 **`SpotNode`의 진짜 상태를 가리키기만 하는 얇은 핸들**이다 … 이런 객체를 facade 패턴이라 부른다(코드 타입 `spot_handle_t`)." |
| admission | "admission 경계를 둔다." | "소켓 HWM 계산과 **받아들일지 말지**(admission) 판단을 분리한다." |

**짝이 되는 개념은 대비 그림으로.** 한쪽을 그리면 짝도 같은 그림틀로 잡는다. 예)
`data plane` = "메시지를 나르는 **외길**", `control plane` = "그 옆에서 관리 정보만 주고받는
**곁길**".

### 8.3 어색한 한자 신조어를 만들지 않는다

영어 jargon을 또 다른 어려운 한자어로 바꾸는 것은 윤문이 아니다. 익숙한 영어를
그대로 두거나, **아예 쉬운 말로 풀어서** 쓴다.

| 나쁜 신조어 | 대신 |
|-------------|------|
| inbound→“인입” | `inbound` 그대로, 또는 “외부에서 들어오는 routed 트래픽”으로 풀어쓰기 |
| egress/outbound→“송출” | `outbound` 그대로, 또는 “바깥으로 내보내는” |

### 8.4 명사 나열(영문 직역체)을 동작·인과로 푼다

문장이 영문처럼 읽히는 가장 큰 이유는 **명사를 그대로 늘어놓아** *누가·무엇을·왜*
하는지의 흐름이 사라지기 때문이다. 한국어 어순으로, 동작과 인과가 보이게 다시 쓴다.

> **Before** (명사 나열 — 한글이어도 영문 같다)
> `Spot` facade는 물리 socket을 직접 만들지 않는다. `SpotNode`가 소유한 transport
> socket에서 demux한 메시지가 대상 `Spot`의 logical queue로 들어온다.
>
> **After** (동작·인과 중심)
> `Spot`은 자기만의 socket을 따로 열지 않는다. 네트워크에 실제로 연결된 transport
> socket은 전부 `SpotNode`가 들고 있고, 여러 `Spot`이 그것을 함께 쓴다. 바깥에서 온
> 메시지는 먼저 `SpotNode`의 socket으로 들어오고, `SpotNode`가 “이 메시지가 어느
> `Spot` 것인지” 가려내(demux) 해당 `Spot`의 메모리 큐에 넣어 준다.

함께 적용할 습관: **긴 한 문장은 끊고**, 같은 뜻의 문장이 두 번 나오면 **하나로 합친다.**

### 8.5 코드에 실재하는 이름은 손대지 않는다

용어를 풀어쓸 때도 **코드 식별자·타입·함수·옵션·enum 상수**는 그대로 둔다
(`SpotNode`, `Spot`, `publish_ingress_queue`, `ZLINK_*`, `zlink_actor_ref_t` 등).
이것들은 독자가 소스와 대조하는 앵커이므로 번역·음차 대상이 아니다. 윤문 대상은
어디까지나 식별자가 **아닌** 일반 단어와 문장 구조다.

### 8.6 이 원칙은 산문에만 적용한다

문체 윤문은 **본문 산문**에만 적용한다. 코드 블록, mermaid/ASCII 다이어그램, 표의
타입·시그니처 칸, 백틱 식별자는 그대로 둔다. 다만 표의 *설명문* 칸도 산문이므로 같은
기준으로 다듬는다.

### 8.7 구어체·판교어(개발자 회의체 표현)를 쓰지 않는다

문서는 말하듯 쓴 초안이 아니라 **전문기술문서**다. 개발자들이 회의·채팅에서 편하게
쓰는 구어체 동사·어미(이른바 "판교어")가 산문에 그대로 남으면, 뜻은 통해도 격식 있는
가이드로 읽히지 않는다. 발견하면 **뜻을 풀어서 쉬운 표준 서술체로** 바꾼다 — 8.1의
전문 용어(영어 그대로 두기)와는 별개 문제다. jargon은 그대로 두되 동사·어미·비유만
격식체로 고친다.

| 구어체/판교어 | 문제 | 대신 |
|---|---|---|
| "그 부분은 framework가 **가져간다**" | 회의체 소유권 표현 | "framework가 **처리한다**/**담당한다**" |
| "라이브러리를 **끌어온다**" | 구어 동사 | "**도입한다**" |
| "그 위에 **얹는다**/**얹으면 된다**" | 구어 동사 | "**추가한다**/**추가로 사용하면 된다**" |
| "그 주제를 **깊게 판다**" | 구어 동사 | "**깊이 집중한다**/**깊이 파고든다**" |
| "나머지 서버는 거의 **논다**" | 사람에게 쓰는 말을 장비에 그대로 씀 | "**유휴 상태로 남는다**" |
| "로드밸런서 **눈에는**" | 구어 관용구 | "로드밸런서 **입장에서는**" |
| "이건 **진짜** 어렵다" | 구어 강조어 | "이는 **실제로** 어렵다" |
| "gRPC 자체는 **빠르고 좋다**" | 구어 서술 | "gRPC 자체의 **성능은 우수하다**" |
| "인프라 박스가 **빠진다**" | 구어 비유 | 비유를 걷어내고 **직접 서술**("인프라 구성 요소가 사라지는 데 있지 않고…") |
| "~하는 **건** 당연하다" (것은→건 축약) | 구어 축약형 | "~하는 **것은** 당연하다" |
| 주어 인격화 제목("gRPC는 **혼자 끝나지 않는다**") | 구어 의인화 | 인격화를 걷어낸 서술("gRPC**만으로는 충분하지 않다**") |

**판별 기준:** 그 문장을 소리 내어 개발자 회의에서 말하면 자연스러운데, 인쇄된
기술서에 그대로 실리면 격이 떨어져 보이면 판교어다. "동사가 사람·구어 상황에서
쓰는 것을 장비·시스템에 그대로 옮겼는가", "축약형·강조어로 말투가 남아 있는가",
"주어를 의인화했는가"로 판별한다.

**8.1과 헷갈리지 말 것:** 8.1은 *명사 jargon*(socket, dispatch, facade)을 한자
번역·음차하지 말고 영어로 두라는 규칙이고, 8.7은 *동사·어미·비유*를 구어체에서
격식체로 바꾸라는 규칙이다. 영어 전문 용어는 8.7 적용 후에도 그대로 남는다.

## 원칙 9 — framework 문서는 언어별로 완결한다 (core/bindings와 반대 전략)

`framework/doc/` 아래 문서는 `doc/`(core·bindings)와 **정반대 전략**을 쓴다.
core·bindings는 "개념은 한 번만, 코드는 언어 탭으로"(원칙 1)로 중복을 없앴다. 하지만
**framework 문서는 언어마다 독립된 완결 문서**를 둔다. 같은 개념이 `.NET` 문서와
`Java` 문서에 따로 설명되는 언어 간 중복을 **의도적으로 허용한다.**

**왜 반대로 가나 — 독자가 다르기 때문이다:**

| | core·bindings 독자 | framework 독자 |
|---|---|---|
| 누구 | 여러 언어를 비교하거나 바인딩을 만드는 사람 | **한 언어로 애플리케이션을 만드는 개발자** (예: .NET 개발자) |
| 기대 | 언어 간 비교, C 계약 확인 | 자기 언어만으로 framework를 처음부터 끝까지 쓰기 |
| 맞는 형태 | concept-once + 탭 | 언어별 완결 문서 |

framework는 각 언어의 idiom으로 감싼 상위 계층이라, 같은 기능도 표현 방식(attribute,
DI, async/await, 빌더 등)이 언어마다 크게 다르다. 이걸 한 문서에 탭으로 묶으면 오히려
읽기 어렵다. 그래서 언어마다 그 언어다운 완결 문서를 따로 쓴다.

**핵심 규칙:**

1. **언어별 완결.** 각 언어 문서(`framework/doc/<컴포넌트>/<lang>/`)는 **그 언어 문서만
   읽고** framework를 이해하고 쓸 수 있어야 한다. "다른 언어 탭을 보라"거나 "core
   문서를 먼저 읽으라"가 전제되면 안 된다.
2. **core는 선택적 심화 링크.** 더 깊이 알고 싶을 때만 core(spec·internals)를 **링크**로
   참고하게 한다. 읽기의 선행 조건이 아니다. framework guide 끝의 "더 깊이" 절이 이
   역할이다 — 본문은 core 없이 완결되고, 링크는 옵션이다.
3. **언어 간 중복은 받아들인다.** 같은 개념을 언어마다 다시 쓰는 비용은 단일 언어
   독자의 완결성을 위해 수용한다. 원칙 1과 정반대 선택이며 의도된 것이다.
4. **공통 scaffolding만 common으로.** 언어와 무관한 정본 sample 시나리오, E2E
   검증 기준, 공통 spec은 `framework/doc/framework/common/`에 두고 언어 문서가
   참조한다. 단 이건 **틀
   (scaffolding) 공유**이지 사용 설명까지 공유하는 게 아니다 — "어떻게 쓰나"는 언어별로
   완결한다.
5. **런타임 공유 언어는 guide만 분리.** Kotlin은 Java 런타임을 공유하므로 **guide만
   Kotlin 고유**(suspend/Flow 등)로 쓰고, spec·internals는 `../java`를 링크로 공유한다.
   bindings에서 Kotlin·JavaScript를 런타임 공유로 처리한 것과 같은 결이다.

**컴포넌트 구성** (셋 다 언어별 디렉토리):

| 컴포넌트 | 위치 | 문서 구성 |
|---|---|---|
| framework | `framework/doc/framework/<lang>/` | `guide` / `spec` / `internals` (+ 공통 `common/`) |
| stream connector | `framework/doc/stream-connector/<lang>/` | `guide` / `core` / `e2e-client` |
| http client | `framework/doc/http-client/<lang>/` | `spec` |

- 언어: `dotnet`, `java`, `kotlin`, `node`, `cpp`. **컴포넌트·언어마다 실제 보유한 하위
  문서는 다르다** (예: kotlin framework는 `guide`만 두고 spec·internals는 java를 링크).
- 각 언어 디렉토리는 `README.ko.md`를 진입점으로 둔다.

**framework의 guide/spec/internals 의미** — 원칙 2의 `doc/`과 성격은 같되 **언어별**이라는
점만 다르다:

- `guide`: 그 언어 개발자가 framework를 **어떻게 쓰나** (완결 튜토리얼, core 없이 읽힘).
- `spec`: 그 언어 framework의 **API 계약**.
- `internals`: framework 구현의 **내부 구조** (필요할 때).

> **새 framework 문서를 쓸 때 자문:** "이 언어 개발자가 *이 문서만* 읽고 framework를 쓸
> 수 있나? core나 다른 언어를 안 봐도 막히지 않나?" — 아니라면 빠진 설명을 그 언어 문서
> 안으로 가져온다. core 링크로 떠넘기지 않는다.

## 원칙 10 — 문서는 현재 상태만 기술한다 (변경 이력은 빼라)

문서는 시스템이 **지금 어떻게 동작하는지**만 적는다. "예전엔 X였다 / Y가 제거됐다 /
이제는 Z가 대신한다 / 표가 갱신됐다" 같은 **변경 이력(changelog)은 빼라.** 그건 git
로그·PR·릴리스 노트의 몫이고, 문서에 남으면 읽는 사람이 사라진 과거 구조까지 머릿속에
담아야 해서 잡음이 된다.

**금지 — changelog식 서술:**

| 나쁜 예 | 왜 빼나 |
|---|---|
| "`internal-router`는 제거되었다." | 지금 없는 걸 굳이 호명한다 |
| "이 소켓들이 맡던 역할은 이제 큐가 대신한다." | 과거 대비 — 현재 사실(큐가 한다)만 적으면 된다 |
| "…행은 존재하지 않는다 / 더 이상 반환하지 않는다." | 없는 것의 부재를 나열할 필요가 없다 |
| "예전 구조에서는 …였다. 그런데 지금은…" | 과거를 끌어와 현재를 설명한다 |
| "perf 표도 이에 맞게 갱신되었다." | 변경 사실 자체가 이력이다 |

**대신:**

- 지금 존재하는 것만 **긍정문**으로: "`zlink_spot_node_internal_sockets()`은 이 socket들을
  보고한다."
- 사라진 것은 **언급하지 않는다.** 표·목록에 없으면 그것으로 끝이다.
- 설계 의도(왜 이런가)는 적되 **과거 대비가 아니라 현재 근거로** 쓴다: "`Spot`은 socket을
  갖지 않는다 — `SpotNode`가 받아 중계하므로 Spot마다 둔 socket HWM이 맞지 않기 때문이다."

**예외 — 런타임 동작의 "제거"는 이력이 아니다.** "Actor가 destroy되면 그 route를
제거한다", "마지막 핸들이 닫힐 때 state가 제거된다"처럼 **시스템이 지금 하는 일**을 적는
건 현재 상태다. 금지 대상은 *문서·코드 구조의 변천사*이지 런타임 동작이 아니다.

## 원칙 11 — 작성 후 Codex 2축 리뷰로 검증한다

문서를 새로 쓰거나 크게 고친 뒤에는 사람 눈만 믿지 말고 **외부 에이전트(Codex)에게
2축 리뷰를 맡긴다.** 원칙 5의 CI가 기계적·구조적 위반(탭 누락, 마크업 급감)을 잡는다면,
이 리뷰는 CI가 못 잡는 **의미 단위의 코드 불일치와 산문 원칙 위반**을 잡는다.

**두 축:**

1. **원칙 준수** — 이 문서(특히 원칙 8 문체, 원칙 10 현재 상태)와 AGENTS.md 규칙을 어겼나.
2. **코드 부합** — 문서가 기술한 동작·구조·시퀀스(mermaid 포함)·자료구조가 실제 구현과
   맞나. 단일 기준은 spec은 `core/include/zlink.h`, internals·guide는 `core/src/`다.

리뷰는 **finding마다 코드 파일:라인 근거**를 달게 하고, 출력은 `[축][심각도] 위치 — 문제 —
근거 — 제안` 형식으로 원칙위반과 코드불일치를 구분한다.

**반영 규칙 (핵심):**

- **finding을 그대로 반영하지 말 것.** 인용된 코드 라인을 직접 읽어 실제 불일치인지
  **검증한 뒤** 고친다. 리뷰어가 "현재 동작"처럼 적은 것이 사실은 미구현 설계일 수 있고,
  그걸 가르는 게 검증이다.
- 검증된 것만 반영하고, 판단이 필요한 항목(설계 blueprint vs 현재 구현 등)은 임의로 고치지
  말고 사람에게 남긴다 — 미구현은 삭제 대신 "설계상 모델 — 미구현" 라벨로 표시(원칙 10과 연결).
- 코드 식별자·타입·mermaid·표 타입칸은 보존하고 산문만 고친다(원칙 8.5/8.6).
- **문서 1개 = 리뷰 1회 = 커밋 1개**로 좁게 묶어, 검증 직후 바로 커밋한다.

**언제:** 새 문서, 큰 개정, 또는 코드가 바뀌어 internals·spec이 흔들릴 수 있을 때. 사소한
오탈자 수정에는 불필요하다.
